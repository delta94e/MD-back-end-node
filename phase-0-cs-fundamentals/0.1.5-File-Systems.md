## 1. File System Là Gì?

File system là **lớp phần mềm** quản lý cách data được tổ chức, lưu trữ và truy xuất trên storage device (SSD/HDD).

```
Application (Node.js)
    │  fs.readFile('/data/users.json')
    ▼
VFS (Virtual File System) ─── abstraction layer
    │
    ├──▶ ext4    (Linux)
    ├──▶ APFS    (macOS)
    ├──▶ NTFS    (Windows)
    └──▶ tmpfs   (RAM-based)
    │
    ▼
Block Device Driver
    │
    ▼
Physical Storage (SSD / HDD)
```

**Giải thích diagram**: Application không bao giờ nói trực tiếp với disk. Nó gọi VFS (Virtual File System) — API chung cho MỌI file system. VFS chuyển request đến driver của file system cụ thể (ext4, APFS...). Đây là ví dụ điển hình của **Adapter pattern** — thay đổi file system mà application không cần sửa code.

### Các File System phổ biến

| File System | OS            | Đặc điểm                                        |
| ----------- | ------------- | ----------------------------------------------- |
| **ext4**    | Linux         | Journaling, extents, mature, default Linux      |
| **XFS**     | Linux         | Tốt cho large files, parallel I/O               |
| **Btrfs**   | Linux         | Copy-on-write, snapshots, checksums             |
| **APFS**    | macOS         | Encryption, snapshots, space sharing            |
| **NTFS**    | Windows       | ACL, compression, encryption                    |
| **ZFS**     | FreeBSD/Linux | Enterprise: RAID + volume manager + file system |

**Follow-up Q: ext4 vs XFS vs ZFS — chọn gì cho server?**

> **ext4**: default, stable, tốt cho hầu hết workloads. **XFS**: tốt hơn cho files lớn (video, database data files) và parallel I/O (nhiều threads ghi cùng lúc). **ZFS**: enterprise-grade với data integrity (checksums mọi block), compression, snapshots, nhưng tốn RAM (1GB RAM / 1TB storage). PostgreSQL production: ext4 hoặc XFS. Docker: overlay2 trên ext4/XFS.

**Follow-up Q: tmpfs là gì? Khi nào dùng?**

> tmpfs = file system nằm hoàn toàn trên RAM (không chạm disk). `/tmp` thường mount trên tmpfs. Dùng cho: temp files, session storage, build artifacts, test data. Ưu: cực nhanh (RAM speed). Nhược: mất khi reboot, giới hạn bởi RAM. Node.js tip: ghi temp files vào `/tmp` thay vì project directory để tận dụng RAM speed.

## 2. Block Storage — Lưu Trữ Theo Khối

### 2.1 Disk không lưu từng byte — mà lưu theo BLOCK

SSD/HDD chia thành các **blocks** (thường 4KB). Đọc/ghi 1 byte cũng phải đọc/ghi nguyên 1 block 4KB.

```
Physical Disk:
┌────────┬────────┬────────┬────────┬────────┬────────┐
│Block 0 │Block 1 │Block 2 │Block 3 │Block 4 │Block 5 │  ...
│ 4KB    │ 4KB    │ 4KB    │ 4KB    │ 4KB    │ 4KB    │
│SuperBlk│Inode   │Inode   │Data    │Data    │Data    │
│        │Table   │Table   │Block   │Block   │Block   │
└────────┴────────┴────────┴────────┴────────┴────────┘
```

### 2.2 Disk Layout (ext4)

```
┌───────────┬──────────────┬─────────────┬──────────────────┐
│ Super     │   Inode      │   Block     │                  │
│ Block     │   Table      │   Bitmap    │   Data Blocks    │
│(metadata) │(file info)   │(free/used)  │(actual content)  │
└───────────┴──────────────┴─────────────┴──────────────────┘
  - Super Block: FS info (block size, total blocks, free blocks)
  - Inode Table: metadata cho mỗi file/directory
  - Block Bitmap: track block nào đang dùng/free
  - Data Blocks: nội dung file thực sự
```

**Giải thích**: Disk được chia thành các vùng. Super Block lưu thông tin tổng thể (như "bìa lịch" của ổ đĩa). Inode Table lưu metadata mọi file. Block Bitmap là "bản đồ" cho biết block nào trống/đã dùng. Data Blocks chứa nội dung file thực sự. Khi tạo file mới: FS tìm free inode → tìm free blocks (qua bitmap) → ghi data → update inode.

**Follow-up Q: Block size 4KB — có lãng phí không?**

> CÓ! File 1 byte vẫn chiếm 4KB disk (internal fragmentation). Nhiều files nhỏ (như `node_modules`) = lãng phí đáng kể. Ví dụ: 100,000 files nhỏ 100 bytes = 100K × 4KB = 400MB disk, nhưng data thực chỉ ~10MB! Giải pháp: ext4 có "inline data" (files <60 bytes lưu trực tiếp trong inode), Btrfs/ZFS có compression.

**Follow-up Q: SSD TRIM là gì? Tại sao quan trọng?**

> SSD không thể ghi đè trực tiếp — phải ERASE block trước rồi mới ghi. Khi xóa file, FS chỉ đánh dấu block là "free" nhưng SSD không biết. TRIM command thông báo cho SSD: "blocks này đã free, có thể erase sẵn". Không TRIM: SSD chậm dần (phải erase on-the-fly khi ghi). Linux: `fstrim` hoặc mount với `discard` option. Docker on SSD: cần enable TRIM!

## 3. Inodes — "Căn Cước" Của File

### 3.1 Inode là gì?

Mỗi file/directory có **đúng 1 inode** — chứa tất cả metadata **trừ tên file**.

```
┌──────────────────────────────────────────┐
│            Inode #12345                   │
├──────────────────────────────────────────┤
│ File Type:      Regular file             │
│ Permissions:    rwxr-xr-x (755)          │
│ Owner UID:      1000                     │
│ Group GID:      1000                     │
│ Size:           13,847 bytes             │
│ Timestamps:                              │
│   Access (atime): 2026-03-01 10:30:00    │
│   Modify (mtime): 2026-02-28 14:15:00   │
│   Change (ctime): 2026-02-28 14:15:00   │
│ Link Count:     2                        │
│ Block Count:    4                        │
│                                          │
│ Data Block Pointers:                     │
│   Direct[0]:     block 1024             │
│   Direct[1]:     block 1025             │
│   Direct[2]:     block 2048             │
│   Direct[3]:     block 5000             │
│   ...                                    │
│   Indirect:      block 6000 ──▶ [ptrs]  │
│   Double Indirect: block 7000           │
│   Triple Indirect: block 8000           │
└──────────────────────────────────────────┘

Tên file KHÔNG nằm trong inode!
Tên file nằm trong directory entry: { "users.json": inode #12345 }
```

### 3.2 Hard Links vs Symbolic Links

```
Hard Link: Nhiều tên → cùng 1 inode (cùng data blocks)
  "file_a.txt"  ─┐
                  ├──▶ Inode #100 ──▶ Data Blocks
  "file_b.txt"  ─┘
  Link count = 2. Xóa file_a → file_b vẫn hoạt động.

Symbolic Link: Tên → trỏ đến path string (shortcut)
  "shortcut" ──▶ Inode #200 ──▶ data = "/path/to/file_a.txt"
  Xóa file_a → shortcut bị broken (dangling symlink)
```

```bash
# Terminal commands
ln file_a.txt file_b.txt        # Hard link
ln -s file_a.txt shortcut       # Symbolic link
ls -li                           # Xem inode numbers
stat file_a.txt                  # Xem chi tiết inode
```

**Follow-up Q: Indirect/Double/Triple pointers hoạt động thế nào?**

> ext4 inode có 12 direct pointers (12 × 4KB = 48KB). File lớn hơn → dùng **Indirect pointer**: trỏ đến block chứa 1024 pointers (1024 × 4KB = 4MB). **Double indirect**: trỏ đến block chứa 1024 indirect pointers (1024² × 4KB = 4GB). **Triple indirect**: 1024³ × 4KB = 4TB. ext4 hiện đại dùng **extents** thay vì block pointers: lưu "block 1000-2000" thay vì 1000 pointers riêng lẻ → hiệu quả hơn nhiều cho files lớn.

**Follow-up Q: Hard link có giới hạn gì?**

> **(1)** KHÔNG thể hard link directories (tránh circular references). **(2)** KHÔNG thể hard link cross file systems (vì inode numbers chỉ unique trong 1 FS). **(3)** Xóa file chỉ thực sự xóa khi link count = 0 AND không có process đang mở file. Docker dùng hard links cho layer sharing (cùng file ở nhiều images).

## 4. File Descriptors — "Tay Cầm" Để Thao Tác File

### 4.1 File Descriptor (fd) là gì?

Khi process mở file, OS trả về một **integer** gọi là file descriptor — đó là "tay cầm" để đọc/ghi file đó.

```
Process file descriptor table:
┌──────┬─────────────────────────────┐
│  fd  │ Trỏ đến                    │
├──────┼─────────────────────────────┤
│  0   │ stdin  (Standard Input)    │  ← luôn mở sẵn
│  1   │ stdout (Standard Output)   │  ← luôn mở sẵn
│  2   │ stderr (Standard Error)    │  ← luôn mở sẵn
│  3   │ /data/users.json           │  ← mới mở
│  4   │ TCP socket (port 3000)     │  ← network connection
│  5   │ /var/log/app.log           │  ← log file
└──────┴─────────────────────────────┘
```

> **"Everything is a file" (Unix philosophy)**: Files, directories, sockets, pipes, devices — tất cả đều access qua file descriptors. Đây là abstraction cực kỳ mạnh.

**Giải thích**: Khi gọi `fs.open()`, kernel tìm slot trống trong FD table của process, tạo entry trỏ đến inode của file, trả về integer (fd). Mọi thao tác sau dùng fd này thay vì path (tránh path resolution lặp lại). fd 0/1/2 (stdin/stdout/stderr) luôn mở sẵn — đây là lý do `console.log()` hoạt động (ghi vào fd 1).

### 4.2 File Descriptor Limit & Leak

```bash
# Xem giới hạn fd
ulimit -n        # Thường 1024 hoặc 65535

# Mỗi connection = 1 fd. Server 10,000 connections = 10,000 fd.
# Nếu không đóng fd → FD LEAK → "Too many open files" error
```

```javascript
// Node.js fd leak example
const fs = require("fs");

// BUG: mở file nhưng không đóng
function readData() {
  const fd = fs.openSync("/data/file.txt", "r");
  const buffer = Buffer.alloc(1024);
  fs.readSync(fd, buffer);
  // fs.closeSync(fd);  ← MISSING! fd bị leak
  return buffer.toString();
}

// FIX: dùng fs.readFileSync() hoặc try/finally
function readDataFixed() {
  const fd = fs.openSync("/data/file.txt", "r");
  try {
    const buffer = Buffer.alloc(1024);
    fs.readSync(fd, buffer);
    return buffer.toString();
  } finally {
    fs.closeSync(fd); // Luôn đóng, kể cả khi error
  }
}

// BEST: dùng high-level API (tự quản lý fd)
const data = fs.readFileSync("/data/file.txt", "utf-8");
```

**Follow-up Q: epoll và fd — liên quan thế nào?**

> `epoll` (Linux) monitor NGANG LÚC nhiều fd (sockets) để biết fd nào có data sẵn. Node.js dùng libuv → epoll (Linux) / kqueue (macOS). 10,000 connections = 10,000 fd, epoll monitor tất cả với O(1) per event. Không cần 10,000 threads! Đây là nền tảng của Node.js non-blocking I/O.

**Follow-up Q: fd inheritance khi fork?**

> Child process kế thừa TẤT CẢ fd của parent (copy fd table). Ví dụ: parent mở socket (fd 3) → child cũng có fd 3 trỏ đến cùng socket. `cluster.fork()` tận dụng điều này: parent mở server socket, fork workers, workers share cùng socket → OS load-balance connections. Flag `CLOEXEC` ngăn fd bị kế thừa khi `exec()` (bảo mật).

## 5. Directory Structure

Directory là **file đặc biệt** chứa danh sách entries: `{ tên_file → inode_number }`.

```
Directory "/home/user/project":
┌──────────────────┬───────────┐
│ Filename         │ Inode #   │
├──────────────────┼───────────┤
│ .                │ 5001      │  (self)
│ ..               │ 5000      │  (parent)
│ package.json     │ 5002      │
│ src/             │ 5003      │
│ node_modules/    │ 5004      │
│ README.md        │ 5005      │
└──────────────────┴───────────┘
```

### Path Resolution

```
Truy cập "/home/user/project/src/app.js":

  1. Inode 2 (root "/")        → tìm entry "home"    → inode 100
  2. Inode 100 ("/home")       → tìm entry "user"    → inode 5000
  3. Inode 5000 ("/home/user") → tìm entry "project" → inode 5001
  4. Inode 5001 ("project")    → tìm entry "src"     → inode 5003
  5. Inode 5003 ("src")        → tìm entry "app.js"  → inode 5010
  6. Đọc inode 5010 → data block pointers → đọc data

  Mỗi "/" = 1 lần đọc directory = 1+ disk I/O
  Path dài = chậm! (OS cache giúp giảm thiểu)
```

**Giải thích**: Truy cập file = duyệt từ root qua từng directory. Mỗi "/" = đọc directory inode → tìm entry → lấy inode tiếp theo. Path 5 levels = 5 lần đọc. OS dùng **dentry cache** (directory entry cache) để cache kết quả — nên lần đầu chậm, lần sau nhanh.

**Follow-up Q: `node_modules` có vấn đề gì với file system?**

> `node_modules` có hàng chục nghìn files nhỏ, nested sâu (path 10+ levels). Vấn đề: **(1)** Nhiều inodes (có thể hết inode dù còn disk!), **(2)** Path resolution chậm, **(3)** `rm -rf node_modules` tốn thời gian (xóa từng file). Giải pháp: pnpm dùng symlinks + content-addressable store, yarn PnP bỏ hẳn `node_modules`.

**Follow-up Q: `.` và `..` là gì trong directory?**

> `.` (dot) = hard link đến chính directory hiện tại. `..` (dotdot) = hard link đến parent directory. Đây là lý do directory mới tạo có link count = 2 (tên trong parent + `.` của chính nó). Mỗi subdirectory thêm 1 link count (vì `..` của child trỏ về parent).

## 6. Journaling — Bảo Vệ Tính Toàn Vẹn

### 6.1 Vấn đề: Crash giữa chừng

Ghi file cần update nhiều thứ: data blocks, inode, bitmap. Nếu **mất điện** giữa chừng → file system **inconsistent** (corrupted).

### 6.2 Journal = Write-Ahead Log

```
Thay vì ghi trực tiếp:

  1. GHI VÀO JOURNAL:    "Sẽ update inode #100 và block #500"
  2. GHI VÀO DISK:       Thực hiện update inode #100 và block #500
  3. XÓA JOURNAL ENTRY:  Đánh dấu hoàn tất

Nếu crash ở bước 2 → khi reboot, đọc journal → redo các thao tác chưa hoàn tất
Nếu crash ở bước 1 → chưa ghi gì → safe, chỉ mất data mới nhất
```

> **Liên hệ**: Đây là chính xác nguyên lý **WAL (Write-Ahead Log)** trong PostgreSQL! Database và file system dùng cùng strategy để đảm bảo durability.

### 6.3 Journaling Modes

| Mode          | Journal chứa                            | Performance | Safety                  |
| ------------- | --------------------------------------- | ----------- | ----------------------- |
| **Journal**   | Metadata + Data                         | Chậm nhất   | An toàn nhất            |
| **Ordered**   | Metadata only (data ghi trước metadata) | Cân bằng    | Tốt                     |
| **Writeback** | Metadata only (data ghi bất kỳ lúc nào) | Nhanh nhất  | Rủi ro file content sai |

**Follow-up Q: `fsync()` là gì? Tại sao database dùng?**

> Khi gọi `write()`, data thường chỉ vào **page cache** (RAM) chưa xuống disk! `fsync(fd)` ép OS flush data từ page cache xuống physical disk. PostgreSQL gọi `fsync()` sau mỗi WAL write để đảm bảo durability. Node.js: `fs.fsync(fd)` hoặc `fs.fdatasync(fd)` (chỉ sync data, không sync metadata — nhanh hơn). Không `fsync` = mất data khi crash!

**Follow-up Q: WAL trong PostgreSQL vs Redis AOF vs MongoDB Journal?**

> Cùng nguyên lý nhưng khác chi tiết: **PostgreSQL WAL**: ghi MỌI thay đổi, replay để recovery + replication. **Redis AOF**: ghi commands (SET, DEL...), rewrite định kỳ để compact. 3 modes: `always` (mỗi command), `everysec` (mỗi giây, default), `no` (OS quyết định). **MongoDB Journal**: ghi changes vào journal trước, flush mỗi 100ms default. Tất cả đều là write-ahead logging!

## 7. Liên Hệ Với Node.js & Backend

| File System Concept | Node.js / Backend                                              |
| ------------------- | -------------------------------------------------------------- |
| File Descriptors    | `fs.open()` trả về fd, socket connections = fd                 |
| Block I/O           | `fs.read()` đọc theo buffer size, Streams dùng `highWaterMark` |
| Journaling / WAL    | PostgreSQL WAL, Redis AOF, MongoDB journal                     |
| Inode timestamps    | `fs.stat()` trả về `atime`, `mtime`, `ctime`                   |
| fd limit            | Server nhiều connections → cần tăng `ulimit -n`                |
| tmpfs               | `/tmp` thường mount trên RAM → nhanh cho temp files            |

```javascript
// Xem file stats (inode info) trong Node.js
const fs = require("fs");
const stats = fs.statSync("package.json");

console.log({
  inode: stats.ino, // Inode number
  size: stats.size, // bytes
  blocks: stats.blocks, // số 512-byte blocks
  hardLinks: stats.nlink, // hard link count
  permissions: stats.mode.toString(8), // octal (e.g., "100644")
  created: stats.birthtime, // creation time
  modified: stats.mtime, // last data modification
  accessed: stats.atime, // last access
  changed: stats.ctime, // last inode change (permissions, etc.)
});
```

**Follow-up Q: Streams trong Node.js và block I/O liên quan thế nào?**

> `fs.readFile()` đọc TOÀN BỘ file vào memory → file 1GB = 1GB RAM! `fs.createReadStream()` đọc từng chunk (default 64KB = `highWaterMark`) — giống đọc từng block. Dùng Streams cho: files lớn, file upload/download, pipe data. Ví dụ: `readStream.pipe(res)` — stream file tới client mà không load toàn bộ vào RAM.

**Follow-up Q: `fs.watch()` vs `fs.watchFile()` — khác gì?**

> `fs.watch()`: dùng OS-level events (inotify trên Linux, FSEvents trên macOS) — NHANH, không poll. `fs.watchFile()`: poll định kỳ bằng `stat()` — chậm, tốn CPU. Luôn dùng `fs.watch()` (hoặc `chokidar` package). `nodemon`, `webpack --watch` dùng inotify/FSEvents bên dưới. Gotcha: Linux inotify có giới hạn watchers (`fs.inotify.max_user_watches` — tăng nếu dự án lớn).

## 8. Câu Hỏi Phỏng Vấn

---

#### Q1: Inode là gì? Tại sao tên file không nằm trong inode?

```
╔══════════════════════════════════════════════════════════════╗
║        TÊN FILE vs INODE — TÁCH BIỆT                    ║
╠══════════════════════════════════════════════════════════════╣
║                                                              ║
║  Directory entry:       Inode #100:                          ║
║  ┌───────────────┐     ┌─────────────────────┐             ║
║  │"app.js"→#100│──►│ size: 1024        │             ║
║  └───────────────┘     │ perms: 644         │             ║
║  ┌───────────────┐     │ owner: user        │             ║
║  │"main.js"→#100│──►│ blocks: [50,51]    │             ║
║  └───────────────┘     │ link_count: 2      │             ║
║  (2 tên → cùng inode)    └─────────────────────┘             ║
║                                                              ║
║  Tách biệt vì: (1) cho phép hard links                       ║
║              (2) rename = chỉ sửa directory, không sửa inode ║
║                                                              ║
╚══════════════════════════════════════════════════════════════╝
```

**Trả lời**: Inode chứa metadata (permissions, size, timestamps, data block pointers). Tên file nằm trong directory entry. Tách biệt vì: (1) cho phép hard links — nhiều tên trỏ đến cùng inode, (2) rename file chỉ cần update directory entry, không sửa inode → atomic và nhanh.

**Follow-up Q: Hết inode nhưng còn disk — có thể xảy ra?**

> CÓ! ext4 cố định số inodes khi format disk. Nhiều files nhỏ (Docker layers, `node_modules`) có thể hết inodes trước khi hết disk. Check: `df -i`. Fix: reformat với nhiều inodes hơn (`mkfs.ext4 -N <count>`), hoặc dùng XFS/Btrfs (tự động allocate inodes).

---

#### Q2: File descriptor là gì? Tại sao "Too many open files"?

> fd là integer mà OS trả về khi process mở file/socket. Mỗi process có giới hạn fd (thường 1024-65535). Server với nhiều connections = nhiều fd. Dò leak: `lsof -p <pid> | wc -l`. Fix: **(1)** đóng connections đúng (try/finally), **(2)** tăng `ulimit -n 65535`, **(3)** dùng connection pooling, **(4)** dùng `fs.readFile()` thay vì `fs.open()` (tự close).

**Follow-up Q: Socket và fd — tại sao mỗi connection tốn 1 fd?**

> "Everything is a file" — TCP connection = file descriptor. Server accept connection → kernel tạo new socket fd. 10,000 concurrent connections = 10,000 fd + 1 server fd. Hệ điệu hành cũng có system-wide limit (`/proc/sys/fs/file-max`). Production: tăng cả user limit và system limit.

#### Q3: Journaling giải quyết vấn đề gì? Liên hệ với database WAL?

```
╔══════════════════════════════════════════════════════╗
║     WRITE-AHEAD LOG PATTERN (chung)                 ║
╠══════════════════════════════════════════════════════╣
║                                                      ║
║  1. Ghi INTENT vào log (sequential, nhanh)           ║
║  2. Ghi thực tế vào data (random, chậm)              ║
║  3. Đánh dấu log entry hoàn tất                       ║
║                                                      ║
║  Crash ở bước 2? → replay log → consistent!          ║
║                                                      ║
║  • ext4 Journal  = file system WAL                   ║
║  • PostgreSQL WAL = database WAL                     ║
║  • Redis AOF      = command log                      ║
║  • MongoDB Journal = operation log                   ║
║                                                      ║
╚══════════════════════════════════════════════════════╝
```

**Follow-up Q: Tại sao sequential write nhanh hơn random write?**

> **HDD**: đầu đọc phải di chuyển vật lý đến vị trí mới (seek ~10ms). Sequential = không cần seek → nhanh gấp 100x. **SSD**: không có seek nhưng sequential vẫn nhanh hơn 2-5x vì: (1) internal parallelism, (2) ít FTL overhead, (3) write amplification thấp hơn. WAL tận dụng: ghi log = sequential (nhanh), ghi data = random (chậm, làm sau).

#### Q4: Node.js đọc file lớn thế nào cho hiệu quả?

> **Sai**: `fs.readFile('big.csv')` — load toàn bộ vào RAM. **Đúng**: dùng Streams. `fs.createReadStream('big.csv', { highWaterMark: 64 * 1024 })` đọc từng 64KB chunk. Kết hợp `readline` cho line-by-line processing. Pipe: `readStream.pipe(transform).pipe(writeStream)` — backpressure tự động. Memory usage: constant ~64KB thay vì toàn bộ file size.

**Follow-up Q: `fs.promises` vs callback vs sync — khi nào dùng?**

> **`fs.promises`** (async/await): production code, không block event loop. **Callback** (`fs.readFile(path, cb)`): legacy code, còn hỗ trợ. **Sync** (`fs.readFileSync`): CHỈ dùng khi startup (load config, read .env) hoặc CLI tools. Dùng sync trong request handler = BLOCK MỌI THỨ. Rule: nếu trong `app.get()` / `app.post()` → luôn dùng async.
