## 1. Process — Tiến Trình

### 1.1 Process là gì?

Process là một **chương trình đang chạy** (program in execution). Khi bạn chạy `node app.js`, OS tạo một process mới.

Mỗi process có:

- **Không gian địa chỉ riêng** (virtual address space) — isolated từ process khác
- **Process Control Block (PCB)** — metadata OS dùng để quản lý

```
┌──────────────────────────────────────────────────────┐
│              Process Control Block (PCB)              │
├────────────────────────┬─────────────────────────────┤
│ Process ID (PID)       │ 12345                       │
│ Process State          │ Running / Ready / Waiting   │
│ Program Counter        │ 0x00401000                  │
│ CPU Registers          │ R0=5, R1=10, ...            │
│ Memory Info            │ Page table pointer           │
│ I/O Status             │ Open files: [fd0, fd1, fd3] │
│ Priority               │ 20                          │
│ Parent PID             │ 12300                       │
│ Scheduling Info        │ CPU time used: 500ms        │
└────────────────────────┴─────────────────────────────┘
```

### 1.2 Process States (Trạng thái process)

```
                    ┌───────────────┐
         Tạo mới   │               │  Kết thúc
  ───────────────▶  │     NEW       │──────────────────▶ TERMINATED
                    │               │
                    └───────┬───────┘
                            │ admitted
                            ▼
                    ┌───────────────┐     I/O hoặc      ┌──────────────┐
                    │               │    event wait      │              │
          ┌────────▶│    READY      │────────────────▶   │   WAITING    │
          │         │  (chờ CPU)    │                    │  (chờ I/O)   │
          │         └───────┬───────┘                    └──────┬───────┘
          │                 │                                   │
          │        scheduler│dispatch              I/O complete │
          │                 ▼                      event occurs │
          │         ┌───────────────┐                           │
          │         │               │                           │
          └─────────│   RUNNING     │◀──────────────────────────┘
           preempt  │  (đang chạy)  │
          (time up) │               │
                    └───────────────┘
```

### 1.3 Process tạo Process (fork)

```
Terminal chạy `node app.js`:

  bash (PID: 100)
    │
    ├──▶ fork() ──▶ node (PID: 101)     ← process con
    │                  │
    │                  ├──▶ fork() ──▶ node worker (PID: 102)  ← cluster
    │                  ├──▶ fork() ──▶ node worker (PID: 103)
    │                  └──▶ fork() ──▶ node worker (PID: 104)
    │
    └── (parent process vẫn chạy)
```

**Giải thích diagram**: `fork()` tạo bản sao của parent process (dùng Copy-on-Write — chỉ copy pages khi GHI). Child process kế thừa: PID mới, cùng code, cùng file descriptors, cùng environment. `cluster.fork()` trong Node.js làm đúng điều này: tạo nhiều worker processes chia sẻ server port.

**Follow-up Q: Zombie process và Orphan process là gì?**

> **Zombie**: child process đã exit nhưng parent chưa gọi `wait()` để đọc exit status → process còn entry trong process table nhưng không chạy. Nhiều zombies = hết PID! Fix: parent phải handle `SIGCHLD` hoặc gọi `waitpid()`. **Orphan**: parent exit trước child → child được `init` (PID 1) nhận nuôi. Không nguy hiểm (init tự động reap). Node.js: `child.unref()` cho phép parent exit mà không đợi child.

**Follow-up Q: Process state diagram — tại sao có cả READY và RUNNING?**

> Vì CPU có hắu hạn cores nhưng nhiều processes. READY = "đã sẵn sàng chạy, chỉ chờ CPU". RUNNING = "đang được CPU thực thi". Trên 4-core CPU, tối đa 4 processes ở RUNNING, phần còn lại ở READY. OS scheduler quyết định khi nào chuyển giữa READY↔RUNNING (preemption). WAITING khác: process đang chờ I/O — dù có CPU rảnh cũng không chạy được.

## 2. Thread — Luồng

### 2.1 Thread là gì?

Thread là **đơn vị thực thi nhỏ nhất** trong một process. Một process có thể có nhiều threads chạy **đồng thời** trong cùng không gian địa chỉ.

```
┌──────────────────────────────────────────────────────────┐
│                     Process                               │
│                                                           │
│  ┌──────────────────────── SHARED ──────────────────────┐│
│  │  Code (Text)  │  Data (Globals)  │  Heap  │  Files   ││
│  └──────────────────────────────────────────────────────┘│
│                                                           │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐      │
│  │  Thread 1   │  │  Thread 2   │  │  Thread 3   │      │
│  │ ─────────── │  │ ─────────── │  │ ─────────── │      │
│  │ Stack       │  │ Stack       │  │ Stack       │      │
│  │ Registers   │  │ Registers   │  │ Registers   │      │
│  │ PC          │  │ PC          │  │ PC          │      │
│  │ Thread ID   │  │ Thread ID   │  │ Thread ID   │      │
│  └─────────────┘  └─────────────┘  └─────────────┘      │
│     (PRIVATE)        (PRIVATE)        (PRIVATE)          │
└──────────────────────────────────────────────────────────┘
```

### 2.2 Shared vs Private

| Shared (chung)         | Private (riêng mỗi thread) |
| ---------------------- | -------------------------- |
| Code segment           | Stack                      |
| Data segment (globals) | Registers (bao gồm PC, SP) |
| Heap                   | Thread ID                  |
| Open files & sockets   | Signal mask                |
| PID                    | errno                      |

**Giải thích**: Thread là "lightweight process" — chia sẻ tài nguyên nặng (code, heap, files) nhưng có stack và registers riêng để chạy độc lập. Lợi ích: tạo/hủy thread nhanh hơn process; bất lợi: một thread crash làm chết toàn bộ process, và shared memory cần synchronization (mutex, semaphore) để tránh race conditions.

**Follow-up Q: User-level threads vs Kernel-level threads?**

> **User-level** (green threads): quản lý bởi runtime (không cần kernel). Nhanh (không system call), nhưng: 1 thread block I/O = TẤT CẢ threads block. Go goroutines là user-level threads multiplexed lên kernel threads (M:N model). **Kernel-level**: OS quản lý, mỗi thread là 1 entity cho scheduler. Tạo chậm hơn (system call), nhưng block 1 thread không ảnh hưởng thread khác. Node.js `worker_threads` là kernel-level threads. libuv thread pool cũng vậy.

**Follow-up Q: Race condition là gì? Ví dụ?**

> 2 threads cùng đọc/ghi 1 biến. Ví dụ: `counter = 0`, Thread A: `counter++`, Thread B: `counter++`. Mong đợi: 2. Thực tế có thể: 1! Vì `counter++` = 3 bước (read → increment → write), nếu cả 2 threads read cùng lúc đều thấy 0 → cả 2 ghi 1. Fix: mutex lock hoặc `Atomics.add()` (Node.js). Node.js single-threaded event loop TRÁNH được vấn đề này — đây là 1 lý do thiết kế single-threaded.

## 3. Process vs Thread — So Sánh Chi Tiết

| Tiêu chí           | Process                                        | Thread                                                     |
| ------------------ | ---------------------------------------------- | ---------------------------------------------------------- |
| **Memory**         | Isolated (riêng hoàn toàn)                     | Shared heap, code, data                                    |
| **Tạo mới**        | Nặng (~ms, copy page tables)                   | Nhẹ (~μs)                                                  |
| **Context Switch** | Chậm (flush TLB, swap page tables)             | Nhanh hơn (cùng address space)                             |
| **Communication**  | IPC (pipes, sockets, shared memory) → phức tạp | Đọc/ghi shared memory → đơn giản nhưng cần synchronization |
| **Crash impact**   | Process crash → chỉ process đó chết            | Thread crash → **toàn bộ process chết**                    |
| **Security**       | Isolated tốt hơn                               | Một thread lỗi có thể corrupt data của thread khác         |
| **Scalability**    | Multi-machine (distributed) dễ hơn             | Giới hạn trong 1 machine                                   |

### Tại sao Node.js chọn single-threaded + multi-process?

```
Lý do chọn Single-Threaded Event Loop:
  1. Không cần locks/mutexes → không deadlock, no race conditions
  2. Developer experience đơn giản — không cần lo thread safety
  3. I/O-bound workloads: single thread đủ (CPU không phải bottleneck)

Khi cần multi-core:
  → cluster module (multi-process) → safe, isolated
  → worker_threads (multi-thread) → share memory khi cần performance
```

**Follow-up Q: Tại sao Node.js không dùng thread pool cho tất cả?**

> libuv có thread pool (default 4 threads) nhưng CHỈ dùng cho: file system I/O, DNS lookup, và một số crypto operations. Network I/O dùng **epoll/kqueue** (non-blocking, không cần thread). Lý do: network I/O có sẵn non-blocking API từ OS, nhưng file system trên Linux KHÔNG có true async I/O (nên cần thread pool giả lập). Tăng pool: `UV_THREADPOOL_SIZE=16 node app.js`.

## 4. Context Switching

### 4.1 Context Switch là gì?

OS chuyển CPU từ chạy Process/Thread A sang Process/Thread B. OS phải **lưu state A** và **load state B**.

```
     Process A running          Context Switch          Process B running
  ┌──────────────────┐    ┌──────────────────────┐    ┌──────────────────┐
  │ Đang thực thi    │    │ 1. Save A's state    │    │ Tiếp tục thực thi│
  │ instruction      │───▶│    (registers, PC,   │───▶│ từ state đã save │
  │                  │    │     page table ptr)  │    │ trước đó         │
  │                  │    │ 2. Load B's state    │    │                  │
  │                  │    │ 3. Flush TLB (nếu    │    │                  │
  │                  │    │    khác process)     │    │                  │
  └──────────────────┘    └──────────────────────┘    └──────────────────┘
                            Cost: ~1-10 μs
                            (+ TLB cold start)
```

### 4.2 Chi phí thực tế

| Loại switch                        | Direct cost                                | Indirect cost                              |
| ---------------------------------- | ------------------------------------------ | ------------------------------------------ |
| **Thread → Thread** (cùng process) | ~1-2 μs (save/load registers)              | Minimal (cùng TLB)                         |
| **Process → Process**              | ~3-5 μs (save/load registers + page table) | TLB flush → TLB misses → ~100s ns per miss |

> **Thread context switch CÓ nhẹ hơn process context switch** — chủ yếu vì không cần flush TLB (cùng address space). Nhưng chi phí direct thì gần nhau, **indirect cost** (TLB cold) mới tạo sự khác biệt lớn.

**Follow-up Q: Voluntary vs Involuntary context switch?**

> **Voluntary**: process tự nhường CPU (gọi I/O, sleep, yield). **Involuntary**: OS cưỡng chế lấy CPU (time slice hết, higher-priority process xuất hiện). Monitor: `cat /proc/<pid>/status | grep ctxt`. Nhiều involuntary switches = CPU contention (quá nhiều processes tranh nhau CPU). Node.js hầu hết là voluntary (chờ I/O callback) — nếu nhiều involuntary = CPU-bound code đang block event loop.

**Follow-up Q: Tại sao container (Docker) chậm hơn bare metal?**

> Không phải vì container = VM! Container dùng CHUNG kernel (không virtualization). Chậm hơn một chút vì: **(1)** overlay filesystem (unionfs) chậm hơn native fs, **(2)** network namespace + bridge thêm latency, **(3)** cgroups enforcement (CPU throttling nếu vượt limit). Nhưng CPU/memory access gần như native (<1% overhead). Performance penalty chủ yếu ở I/O-heavy workloads.

## 5. CPU Scheduling Algorithms

OS cần quyết định process/thread nào được chạy tiếp khi CPU rảnh.

### 5.1 Các thuật toán phổ biến

**FCFS (First Come First Served)**:

```
Process:    P1(24ms)    P2(3ms)    P3(3ms)
Thứ tự:    P1 ──────────────────────▶ P2 ──▶ P3 ──▶
Wait time: P1=0, P2=24, P3=27.  Average = 17ms

Vấn đề: "Convoy effect" — process ngắn phải chờ process dài
```

**SJF (Shortest Job First)**:

```
Thứ tự:    P2 ──▶ P3 ──▶ P1 ──────────────────────▶
Wait time: P2=0, P3=3, P1=6.  Average = 3ms  (OPTIMAL cho average wait!)

Vấn đề: Starvation — process dài có thể không bao giờ được chạy
         Không thể biết trước burst time
```

**Round Robin (RR)**:

```
Time quantum = 4ms

P1(24) → P2(3) → P3(3) → P1(20) → P1(16) → P1(12) → ...
  4ms      3ms     3ms     4ms       4ms       4ms

Ưu điểm: Fair, response time tốt (time-sharing systems)
Nhược điểm: Context switch overhead nếu quantum quá nhỏ
```

**Priority Scheduling**:

```
Mỗi process có priority. Priority cao chạy trước.
Vấn đề: Starvation (priority thấp bị bỏ đói)
Giải pháp: Aging — tăng priority theo thời gian chờ
```

**Multilevel Feedback Queue (Linux CFS)**: Linux dùng **Completely Fair Scheduler** — mỗi process được chia thời gian CPU tỷ lệ thuận với weight (dựa trên nice value). Dùng red-black tree để O(log n) pick next process.

**Follow-up Q: Linux `nice` value ảnh hưởng Node.js thế nào?**

> `nice` value từ -20 (ưu tiên cao) đến 19 (ưu tiên thấp). Default = 0. `nice -n -10 node app.js` cho Node.js ưu tiên cao hơn. Dùng cho: production servers chạy cùng với batch jobs. CFS đảm bảo mỗi process được CPU time tỷ lệ với weight — process nice=-10 được ~4x CPU time so với nice=0.

**Follow-up Q: Node.js event loop có phải là "scheduler" không?**

> Đúng! Event loop là **application-level scheduler**: nó quyết định callback nào chạy tiếp. Phases: timers → pending callbacks → poll (I/O) → check (setImmediate) → close. Khác OS scheduler: event loop không preempt (1 callback chạy HẾ T mới chạy callback tiếp). Nên 1 callback tốn 100ms = block 100ms. OS scheduler preempt mỗi ~4ms.

## 6. Deadlock

### 6.1 Deadlock là gì?

Hai hay nhiều processes **chờ đợi lẫn nhau** giữ resource, không ai nhường → tất cả đều bị block vĩnh viễn.

```
  Thread A                    Thread B
  ──────────                  ──────────
  Lock(Resource1) ✅          Lock(Resource2) ✅
       │                           │
  Đợi Resource2... ⏳         Đợi Resource1... ⏳
       │                           │
       └───── DEADLOCK! ──────────┘
       Cả hai chờ nhau mãi mãi
```

### 6.2 Bốn điều kiện Coffman (cần và đủ)

Deadlock xảy ra **khi và chỉ khi** cả 4 điều kiện đồng thời tồn tại:

| #   | Điều kiện            | Giải thích                                           |
| --- | -------------------- | ---------------------------------------------------- |
| 1   | **Mutual Exclusion** | Resource chỉ 1 process dùng tại 1 thời điểm          |
| 2   | **Hold and Wait**    | Process giữ resource này trong khi chờ resource khác |
| 3   | **No Preemption**    | Resource không thể bị cưỡng bức lấy lại              |
| 4   | **Circular Wait**    | Tồn tại vòng tròn chờ: A→B→C→A                       |

### 6.3 Phòng tránh Deadlock

| Phá điều kiện     | Cách làm                                                   |
| ----------------- | ---------------------------------------------------------- |
| Mutual Exclusion  | Dùng read-only resources khi có thể                        |
| Hold and Wait     | Yêu cầu tất cả resources cùng lúc (atomic)                 |
| No Preemption     | Cho phép timeout → release resources                       |
| **Circular Wait** | **Lock ordering** — luôn acquire locks theo thứ tự cố định |

### 6.4 Ví dụ thực tế (Database)

```sql
-- Transaction A:                      -- Transaction B:
BEGIN;                                  BEGIN;
UPDATE accounts SET bal=bal-100         UPDATE accounts SET bal=bal-50
  WHERE id=1;  -- Lock row 1             WHERE id=2;  -- Lock row 2

UPDATE accounts SET bal=bal+100         UPDATE accounts SET bal=bal+50
  WHERE id=2;  -- Chờ row 2!             WHERE id=1;  -- Chờ row 1!

-- DEADLOCK! PostgreSQL sẽ detect và rollback 1 transaction
```

### 6.5 Deadlock trong Node.js?

Node.js single-threaded → **không có traditional deadlock** (không có locks). Nhưng có thể gặp **logical deadlock** dạng:

- Promise chờ Promise (circular dependency)
- Distributed deadlock (Service A gọi Service B, B gọi A, cả hai đợi response)

```javascript
// Logical deadlock: circular Promise dependency
const a = new Promise((resolve) => {
  b.then(() => resolve("a done")); // a chờ b
});
const b = new Promise((resolve) => {
  a.then(() => resolve("b done")); // b chờ a
});
// → Cả hai Promise sẽ pending mãi mãi
```

**Follow-up Q: Distributed deadlock xảy ra thế nào?**

> Service A gọi Service B (chờ response), đồng thời Service B gọi Service A (chờ response). Cả hai block mãi! Không có "global lock manager" để detect. Fix: **(1)** timeout cho mọi HTTP/gRPC call (ví dụ: 5s), **(2)** circuit breaker pattern (fall fast), **(3)** async events thay vì sync calls (Event-Driven Architecture), **(4)** ordering: A luôn gọi B, không bao giờ ngược lại.

**Follow-up Q: Dining Philosophers problem là gì?**

> Bài toán kinh điển: 5 triết gia ngồi quanh bàn, 5 đũa. Mỗi người cần 2 đũa để ăn nhưng chỉ có thể cầm 1 đũa mỗi lần. Nếu tất cả cùng cầm đũa trái → không ai có đũa phải → deadlock! Giải pháp: 1 người cầm đũa PHẢI trước (phá circular wait) hoặc dùng semaphore giới hạn max 4 người ăn cùng lúc.

## 7. Inter-Process Communication (IPC)

Processes có memory riêng biệt → cần cơ chế giao tiếp:

| Phương pháp           | Tốc độ         | Mô tả                                                            |
| --------------------- | -------------- | ---------------------------------------------------------------- |
| **Pipe**              | Nhanh          | Unidirectional byte stream giữa parent-child                     |
| **Named Pipe (FIFO)** | Nhanh          | Pipe có tên trong file system, không cần parent-child            |
| **Message Queue**     | Trung bình     | Kernel quản lý queue, structured messages                        |
| **Shared Memory**     | **Nhanh nhất** | Cùng physical memory mapped vào 2 processes. Cần synchronization |
| **Socket**            | Linh hoạt      | TCP/UDP, hoạt động cả local và network                           |
| **Signal**            | Đơn giản       | Thông báo sự kiện (SIGTERM, SIGKILL, SIGUSR1)                    |
| **Semaphore**         | Đồng bộ        | Counting mechanism cho resource access                           |

### Node.js IPC

```javascript
// Parent-child IPC qua fork()
// parent.js
const { fork } = require("child_process");
const child = fork("./child.js");

child.send({ type: "COMPUTE", data: [1, 2, 3] }); // IPC channel
child.on("message", (result) => console.log("Result:", result));

// child.js
process.on("message", (msg) => {
  if (msg.type === "COMPUTE") {
    const sum = msg.data.reduce((a, b) => a + b, 0);
    process.send({ type: "RESULT", value: sum }); // gửi về parent
  }
});
```

**Follow-up Q: SharedArrayBuffer vs IPC message passing?**

> **IPC message** (process.send): serialize → copy → deserialize. An toàn (không share memory) nhưng CHẬM cho data lớn. **SharedArrayBuffer** (worker_threads): cùng vùng memory, không copy → CỰC NHANH. Nhưng cần `Atomics` để synchronization. Dùng khi: transfer data lớn giữa workers (vd: image processing, ML inference). Không dùng khi: đơn giản chỉ cần send command/result.

**Follow-up Q: Unix domain socket vs TCP socket cho IPC?**

> **Unix socket**: chỉ hoạt động trên CÙNG máy, không qua network stack → nhanh gấp ~2x TCP local. Dùng: communication giữa containers trên cùng host, Docker socket (`/var/run/docker.sock`), Nginx ↔ PHP-FPM. **TCP socket**: qua network stack (cả khi localhost) → chậm hơn nhưng linh hoạt (làm việc qua network). Node.js IPC (cluster) dùng Unix domain socket trên Linux/Mac.

## 8. Concurrency vs Parallelism

```
Concurrency (đồng thời):
  Nhiều tasks TIẾN TRIỂN cùng lúc, nhưng có thể không thực sự chạy song song.
  Single-core: OS chuyển đổi nhanh giữa tasks (time-slicing)

    Core 0:  ─A─B─A─C─B─A─C─B─  (interleaved)

Parallelism (song song):
  Nhiều tasks THỰC SỰ chạy cùng lúc trên nhiều cores.

    Core 0:  ─A─A─A─A─A─A─A─A─
    Core 1:  ─B─B─B─B─B─B─B─B─
    Core 2:  ─C─C─C─C─C─C─C─C─
```

> **Node.js**: Concurrent (event loop xử lý nhiều requests cùng lúc) nhưng NOT parallel trên single thread. Dùng `cluster`/`worker_threads` để đạt parallelism.

**Follow-up Q: async/await có phải là concurrency không?**

> CÓ! `async/await` là **cooperative concurrency**: khi gặp `await`, function YIELD control về event loop → event loop chạy task khác. Giống coroutines: không phải parallelism (chỉ 1 thread) nhưng nhiều tasks tiến triển cùng lúc. Khác threads: không bị preempt (chỉ yield tại await), không cần locks. `Promise.all()` = concurrent I/O, `for...of` + `await` = sequential.

**Follow-up Q: C10K Problem là gì? Node.js giải quyết thế nào?**

> Thữ thách handle 10,000 concurrent connections. Thread-per-connection: 10,000 threads × 1MB stack = 10GB RAM + context switch overhead. Node.js: 1 thread + event loop + non-blocking I/O = handle 10K+ connections với ~50MB RAM. epoll (Linux) cho phép monitor hàng nghìn file descriptors hiệu quả (O(1) per event). Nginx cũng dùng cùng approach.

## 9. Liên Hệ Với Node.js

| OS Concept | Node.js Equivalent                                                                  |
| ---------- | ----------------------------------------------------------------------------------- |
| Process    | `node app.js` = 1 OS process                                                        |
| fork()     | `child_process.fork()`, `cluster.fork()`                                            |
| Thread     | Event loop = main thread, libuv = thread pool (4 threads), `worker_threads`         |
| IPC        | `process.send()` / `process.on('message')`                                          |
| Signal     | `process.on('SIGTERM')`, `process.kill(pid, signal)`                                |
| Scheduling | OS scheduler. Node.js event loop là **application-level scheduler** cho async tasks |
| Mutex/Lock | Không cần (single-threaded). `worker_threads` dùng `Atomics` + `SharedArrayBuffer`  |

**Follow-up Q: Graceful shutdown trong Node.js dùng signals thế nào?**

```javascript
// Production-ready graceful shutdown
process.on("SIGTERM", async () => {
  console.log("SIGTERM received. Shutting down gracefully...");

  // 1. Ngừng nhận connection mới
  server.close(() => {
    console.log("HTTP server closed.");
  });

  // 2. Chờ requests đang xử lý hoàn thành (timeout 30s)
  setTimeout(() => {
    console.error("Forced shutdown after timeout");
    process.exit(1);
  }, 30000);

  // 3. Đóng database connections
  await db.close();
  await redis.quit();

  process.exit(0);
});
// Docker/K8s gửi SIGTERM trước, chờ 30s, rồi SIGKILL
```

## 10. Câu Hỏi Phỏng Vấn

---

#### Q1: Process vs Thread khác nhau thế nào ở mức OS?

```
╔══════════════════════════════════════════════════════════════╗
║               2 PROCESSES vs 2 THREADS                   ║
╠══════════════════════════════════════════════════════════════╣
║                                                              ║
║  2 PROCESSES:             2 THREADS (cùng process):         ║
║  ┌─────────┐ ┌───────┐  ┌─────────────────────────┐       ║
║  │Code     │ │Code   │  │  CODE (shared)        │       ║
║  │Data     │ │Data   │  │  DATA (shared)        │       ║
║  │Heap     │ │Heap   │  │  HEAP (shared)        │       ║
║  │Stack    │ │Stack  │  │  ┌──────┐ ┌───────┐ │       ║
║  │Files    │ │Files  │  │  │Stack1│ │Stack2 │ │       ║
║  └─────────┘ └───────┘  │  └──────┘ └───────┘ │       ║
║  (isolated 100%)         └─────────────────────────┘       ║
║                            (shared — cần sync!)             ║
║                                                              ║
╚══════════════════════════════════════════════════════════════╝
```

**Trả lời**: Process có isolated virtual address space (riêng page table, code, data, heap, stack). Thread chia sẻ address space (chung code, data, heap, files) nhưng có stack và registers riêng. Tạo process cần setup page tables (~ms), tạo thread chỉ cần allocate stack (~μs). Process crash chỉ ảnh hưởng process đó; thread crash làm chết cả process.

**Follow-up Q: Khi nào chọn process, khi nào chọn thread?**

> **Process**: khi cần isolation (service khác nhau, untrusted code), crash recovery (độc lập), multi-machine scaling. **Thread**: khi cần share data nhiều, communication nhanh, memory efficiency. Node.js: `cluster` (multi-process) cho HTTP scaling, `worker_threads` (multi-thread) cho CPU-intensive tasks.

---

#### Q2: Context switch của thread có thực sự nhẹ hơn process không?

> Direct cost gần bằng nhau (~1-5μs). Nhưng **indirect cost** khác biệt lớn: process switch thay đổi page table pointer → TLB flush → mỗi memory access đều TLB miss. Thread switch giữ nguyên address space → TLB entries vẫn valid. Khác biệt thực tế: ~3-10x chậm hơn cho process switch (vì TLB cold start).

---

#### Q3: Deadlock — 4 điều kiện và cách phòng tránh?

> (1) Mutual Exclusion, (2) Hold and Wait, (3) No Preemption, (4) Circular Wait. Phá Circular Wait hiệu quả nhất: **Lock Ordering** — luôn acquire locks theo cùng thứ tự. Database: timeout (`SET lock_timeout`) + deadlock detection (PostgreSQL tự detect và rollback victim). Distributed: TTL locks, circuit breakers.

**Follow-up Q: Node.js không có locks nhưng có race conditions không?**

> CÓ! Ví dụ: 2 API requests cùng đọc balance, cùng trừ tiền, cùng ghi lại → lost update. Dù single-threaded, I/O gaps (await) cho phép interleaving. Fix: **(1)** Optimistic locking (`UPDATE WHERE version=X`), **(2)** Database transactions (`SERIALIZABLE`), **(3)** Redis WATCH/MULTI, **(4)** `LOCK` trong application (mutex cho async code: `async-mutex` npm package).

---

#### Q4: SIGTERM vs SIGKILL khác gì?

> **SIGTERM** (15): "xiên đẹp" — process NHẬN được và có thể handle (cleanup, close connections, flush data). **SIGKILL** (9): "giết ngay" — process KHÔNG nhận được, kernel giết trực tiếp (resources leak!). Docker/K8s: gửi SIGTERM → chờ 30s (configurable) → SIGKILL. Luôn handle SIGTERM để graceful shutdown!

#### Q5: Giải thích Node.js event loop phases.

```
╔══════════════════════════════════════════════════════╗
║          NODE.JS EVENT LOOP PHASES                  ║
╠══════════════════════════════════════════════════════╣
║                                                      ║
║   → [1] TIMERS           setTimeout, setInterval     ║
║   → [2] PENDING CALLBACKS  system errors, TCP errors  ║
║   → [3] IDLE/PREPARE      (internal)                  ║
║   → [4] POLL              I/O callbacks (fs, net)     ║
║   → [5] CHECK             setImmediate               ║
║   → [6] CLOSE CALLBACKS   socket.on('close')         ║
║                                                      ║
║   Giữa mỗi phase:                                     ║
║   • process.nextTick() → chạy TRƯỚC phase tiếp       ║
║   • Promise microtasks → chạy SAU nextTick            ║
║                                                      ║
╚══════════════════════════════════════════════════════╝
```

**Trả lời**: Event loop chạy qua 6 phases vòng tròn. Poll phase là quan trọng nhất: đợi I/O events và chạy callbacks. `process.nextTick()` và microtasks (Promise.then) chạy GIỮA các phases — có ưu tiên cao nhất. Nhiều `nextTick()` có thể starve I/O (không bao giờ đến poll phase).
