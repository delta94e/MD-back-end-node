## 1. Tổng Quan Phân Cấp Bộ Nhớ

```
            Tốc độ ▲        Chi phí/GB ▲        Dung lượng
                   │                   │
  Registers ──────►│  ~0.3ns          │  $$$$$$$     │  ~KB
                   │                   │              │
  L1 Cache ───────►│  ~1ns            │  $$$$$$      │  32-64KB
                   │                   │              │
  L2 Cache ───────►│  ~4ns            │  $$$$$       │  256KB-1MB
                   │                   │              │
  L3 Cache ───────►│  ~12ns           │  $$$$        │  8-64MB
                   │                   │              │
  RAM ────────────►│  ~100ns          │  $$$         │  8-128GB
                   │                   │              │
  SSD ────────────►│  ~100μs          │  $$          │  256GB-4TB
                   │                   │              │
  HDD ────────────►│  ~10ms           │  $           │  1-20TB
                   │                   │              ▼
                   │                   │         Lớn nhất
              Nhanh nhất          Đắt nhất
```

**Giải thích diagram**: Memory hierarchy là hình kim tự tháp — tầng trên càng nhanh, càng nhỏ, càng đắt. Tầng dưới càng chậm, càng lớn, càng rẻ. CPU luôn tìm data từ tầng nhanh nhất trước (registers → L1 → L2 → L3 → RAM → disk). Nếu không tìm thấy ("miss"), mới xuống tầng chậm hơn.

**Nguyên lý cốt lõi**: Không thể có bộ nhớ vừa nhanh, vừa lớn, vừa rẻ. Nên hệ thống phân tầng: **data "hot" nằm ở tầng nhanh, data "cold" nằm ở tầng chậm**.

### So sánh con số thực tế

Nếu 1 CPU cycle = 1 giây (quy đổi thời gian cho dễ hình dung):

| Thao tác                  | Thời gian thực | Quy đổi tương đương |
| ------------------------- | -------------- | ------------------- |
| L1 Cache hit              | ~1 ns          | **1 giây**          |
| L2 Cache hit              | ~4 ns          | 4 giây              |
| L3 Cache hit              | ~12 ns         | 12 giây             |
| RAM access                | ~100 ns        | **1.5 phút**        |
| SSD random read           | ~100 μs        | **1.5 ngày**        |
| HDD seek                  | ~10 ms         | **5 tháng**         |
| Network (same DC)         | ~500 μs        | **1 tuần**          |
| Network (cross-continent) | ~150 ms        | **4.5 năm**         |

> Khi bạn đọc 1 byte từ disk thay vì cache, tương đương với việc chờ **5 tháng** thay vì **1 giây**. Đây là lý do caching quan trọng đến vậy.

**Follow-up Q: Tại sao backend developer cần biết những con số này?**

> Vì mọi quyết định thiết kế đều liên quan đến latency: **Redis** (~1ms) nhanh gấp ~10x so với **PostgreSQL** (~10ms). **CDN** (same region, ~5ms) nhanh gấp ~30x so với origin server (cross-continent, ~150ms). **In-memory cache** (RAM, ~100ns) nhanh gấp ~1000x so với SSD read. System design interview luôn hỏi "tại sao đặt cache ở đây?" — câu trả lời luôn quay về memory hierarchy.

**Follow-up Q: Latency numbers cần nhớ cho system design?**

> Bảng này gọi là "Jeff Dean's Latency Numbers Every Programmer Should Know". Cần nhớ: L1=1ns, RAM=100ns, SSD=100μs, HDD=10ms, same-DC network=500μs, cross-continent=150ms. Mẹo: mỗi tầng chậm hơn tầng trước khoảng 10-100x.

## 2. RAM — Random Access Memory

### 2.1 RAM là gì?

RAM là bộ nhớ chính (main memory) — nơi chương trình đang chạy và data đang xử lý được lưu trữ.

**Đặc điểm**:

- **Random Access**: Truy cập bất kỳ vị trí nào đều mất cùng thời gian (~100ns)
- **Volatile**: Mất dữ liệu khi tắt nguồn (khác SSD/HDD)
- **Byte-addressable**: Mỗi byte có một địa chỉ duy nhất

### 2.2 RAM vs ROM

| Đặc điểm | RAM                             | ROM                            |
| -------- | ------------------------------- | ------------------------------ |
| Đọc/Ghi  | Cả hai                          | Chỉ đọc (hoặc ghi rất chậm)    |
| Volatile | Có (mất khi tắt nguồn)          | Không                          |
| Tốc độ   | Nhanh                           | Chậm hơn                       |
| Vai trò  | Lưu data chương trình đang chạy | Lưu firmware, BIOS, bootloader |

### 2.3 DRAM vs SRAM

```
SRAM (Static RAM):
  - Dùng cho CPU Cache (L1, L2, L3)
  - 6 transistors / bit → đắt, nhưng cực nhanh
  - Không cần refresh

DRAM (Dynamic RAM):
  - Dùng cho Main Memory (RAM stick)
  - 1 transistor + 1 capacitor / bit → rẻ, lớn, nhưng chậm hơn
  - Cần refresh mỗi ~64ms (capacitor leak charge)
```

**Giải thích**: SRAM (dùng 6 transistors/bit) giữ data bằng mạch flip-flop — cực nhanh, không cần refresh, nhưng đắt và tốn diện tích. DRAM (1 transistor + 1 capacitor/bit) lưu data bằng điện tích capacitor — rẻ hơn ~10x nhưng cần refresh liên tục (capacitor rỉ điện). Đây là lý do cache (SRAM) nhỏ và đắt, RAM (DRAM) lớn và rẻ hơn.

**Follow-up Q: ECC RAM là gì? Tại sao server cần?**

> ECC (Error-Correcting Code) RAM phát hiện và sửa lỗi 1-bit tự động. Cosmic rays và nhiễu điện có thể "flip" bit ngẫu nhiên (bit flip/soft error). Server có hàng trăm GB RAM chạy 24/7 → xác suất bit flip cao. Google từng báo cáo: ~1 bit flip / 1GB / 18 giờ! ECC RAM đắt hơn ~10-20% nhưng bắt buộc cho servers/databases.

**Follow-up Q: DDR4 vs DDR5 — khác gì cho backend?**

> DDR5: bandwidth gấp đôi DDR4 (4800-6400 MT/s vs 2133-3200 MT/s), nhưng LATENCY gầN BẰNG (~14ns first-byte). Với backends: bandwidth quan trọng cho big data/analytics (scan nhiều data). Latency quan trọng cho OLTP (nhiều random small reads). Redis, Memcached hưởng lợi từ bandwidth (value streaming). PostgreSQL hưởng lợi từ cả hai (buffer pool + sequential scan).

## 3. Virtual Memory — Bộ Nhớ Ảo

### 3.1 Vấn đề: Tại sao cần Virtual Memory?

**Không có Virtual Memory** (thời kỳ đầu):

- Mỗi chương trình truy cập **physical memory** trực tiếp
- Chương trình A có thể vô tình ghi đè memory của chương trình B → **crash**
- Nếu RAM 4GB nhưng chương trình cần 8GB → **không chạy được**
- Mỗi chương trình phải biết chính xác nó được load ở địa chỉ nào → **phức tạp**

**Với Virtual Memory** (giải pháp):

- Mỗi process có **không gian địa chỉ ảo** riêng (thường 4GB trên 32-bit, 128TB+ trên 64-bit)
- Process nghĩ nó "sở hữu" toàn bộ memory → đơn giản hóa lập trình
- OS ánh xạ (map) virtual addresses → physical addresses
- Hai process CÓ THỂ dùng cùng virtual address nhưng trỏ đến physical address khác nhau → **isolation**

### 3.2 Cách Virtual Memory hoạt động

```
              Process A                    Physical RAM            Process B
          (Virtual Memory)                                    (Virtual Memory)
       ┌──────────────────┐           ┌──────────────────┐  ┌──────────────────┐
       │ 0x0000: Code     │───────┐   │ Frame 0: A code  │  │ 0x0000: Code     │
       │ 0x1000: Data     │──┐    └──▶│ Frame 1: B data  │◄─│ 0x1000: Data     │
       │ 0x2000: Heap     │  │    ┌──▶│ Frame 2: A data  │  │ 0x2000: Heap     │
       │ 0x3000: (unused) │  └────┘   │ Frame 3: A heap  │  │ 0x3000: Stack    │
       │ ...              │       ┌──▶│ Frame 4: B code  │◄─│                  │
       │ 0xFFFF: Stack    │───┐   │   │ Frame 5: B heap  │  │ 0xFFFF: Stack    │
       └──────────────────┘   │   │   │ Frame 6: (free)  │  └──────────────────┘
                              │   │   │ Frame 7: A stack │
                              └───┘   │ Frame 8: B stack │
                                      └──────────────────┘

    Cùng virtual address 0x1000   → khác physical address!
    A's 0x1000 → Frame 2          B's 0x1000 → Frame 1
```

**3 lợi ích chính**:

1. **Isolation**: Process A không thể đọc/ghi memory của Process B
2. **Abstraction**: Developer không cần quan tâm physical memory layout
3. **Overcommit**: Tổng virtual memory > physical RAM (dùng disk swap)

**Giải thích diagram**: Mỗi process "được thấy" toàn bộ không gian địa chỉ (0x0000→0xFFFF) như của riêng mình. Trên thực tế, OS ánh xạ các pages của mỗi process sang các frames KHAC NHAU trong physical RAM. Cùng virtual address 0x1000 của process A và B trỏ đến vị trí vật lý khác nhau → isolation hoàn toàn.

**Follow-up Q: `mmap` là gì? Tại sao quan trọng?**

> `mmap` ánh xạ file trực tiếp vào virtual memory. Thay vì `read()` file vào buffer (copy data), `mmap` cho phép đọc file như đọc array trong memory — OS tự load pages khi cần (lazy). **Ưu**: zero-copy, hiệu quả cho file lớn, nhiều processes có thể share cùng mapping. **Nhược**: khó handle errors, không kiểm soát được I/O timing. PostgreSQL, MongoDB, SQLite đều dùng mmap cho data files.

**Follow-up Q: Copy-on-Write (COW) là gì?**

> Khi `fork()` process con, OS KHÔNG copy toàn bộ memory — chỉ share cùng physical pages và đánh dấu read-only. Khi process con GHI vào page → page fault → OS copy riêng page đó rồi mới ghi. Tiết kiệm memory và thời gian fork. Redis `BGSAVE` dùng COW: fork child process, child ghi RDB file từ memory, parent tiếp tục serve — chỉ pages bị sửa mới bị copy.

## 4. Paging — Phân Trang

### 4.1 Page là gì?

Virtual memory được chia thành **pages** (trang) cố định, thường **4KB** mỗi page. Physical memory được chia thành **frames** cùng kích thước. OS duy trì **Page Table** để ánh xạ page → frame.

```
                    Page Table (mỗi process có riêng)
Virtual Memory      ┌────────┬────────┬───────┐     Physical Memory
 ┌──────────┐       │ Page # │Frame # │ Valid │      ┌──────────┐
 │ Page 0   │──────▶│   0    │   5    │   1   │─────▶│ Frame 5  │
 │ Page 1   │──────▶│   1    │   2    │   1   │─────▶│ Frame 2  │
 │ Page 2   │──────▶│   2    │   -    │   0   │ (on disk!)
 │ Page 3   │──────▶│   3    │   8    │   1   │─────▶│ Frame 8  │
 │ Page 4   │──────▶│   4    │   1    │   1   │─────▶│ Frame 1  │
 └──────────┘       └────────┴────────┴───────┘      └──────────┘

 Valid = 1: page đang ở RAM
 Valid = 0: page ở disk (cần load vào RAM khi truy cập)
```

### 4.2 Address Translation (Chuyển đổi địa chỉ)

```
Virtual Address = Page Number + Offset

Ví dụ (page size = 4KB = 4096 bytes = 2^12):
  Virtual Address: 0x00003A7F

  Page Number = 0x00003A7F >> 12 = 0x3   (3 bits cao)
  Offset      = 0x00003A7F & 0xFFF = 0xA7F  (12 bits thấp)

  Tra page table: Page 3 → Frame 8
  Physical Address = Frame 8 * 4096 + 0xA7F = 0x8A7F
```

### 4.3 Multi-level Page Tables

Process 64-bit có 2⁶⁴ virtual addresses → single-level page table quá lớn. Giải pháp: **multi-level page table** (x86-64 dùng 4 levels).

```
Virtual Address (48-bit dùng trên x86-64):
┌──────┬──────┬──────┬──────┬────────────┐
│ PML4 │ PDP  │  PD  │  PT  │   Offset   │
│ 9bit │ 9bit │ 9bit │ 9bit │   12bit    │
└──┬───┴──┬───┴──┬───┴──┬───┴─────┬──────┘
   │      │      │      │         │
   ▼      ▼      ▼      ▼         ▼
  Level4→Level3→Level2→Level1→ Physical Frame + Offset
```

Lợi ích: Chỉ cần allocate page table entries cho vùng memory **thực sự dùng**, tiết kiệm rất nhiều RAM.

**Follow-up Q: Huge Pages là gì? Tại sao database dùng?**

> Page thường = 4KB. Huge Pages = 2MB hoặc 1GB. Lợi ích: ít page table entries hơn → ít TLB misses hơn. Ví dụ: 1GB data = 262,144 pages (4KB) nhưng chỉ 512 huge pages (2MB). PostgreSQL, Redis, MongoDB đều khuyến nghị Huge Pages cho production (cấu hình `vm.nr_hugepages` trên Linux). Nhược: không thể swap, phải pre-allocate, có thể lãng phí nếu data nhỏ.

**Follow-up Q: Tại sao page size là 4KB mà không phải 1KB hay 1MB?**

> Trade-off: page nhỏ (1KB) → page table lớn, nhiều TLB misses, nhưng ít internal fragmentation (lãng phí). Page lớn (1MB) → page table nhỏ, ít TLB misses, nhưng lãng phí nhiều (allocate 1 byte vẫn tốn 1MB). 4KB là thỏa hiệp tối ưu cho hầu hết workloads, được chọn từ thời VAX (1977) và giữ đến nay.

## 5. Page Faults — Lỗi Trang

### 5.1 Khi nào xảy ra?

Khi CPU truy cập virtual address mà page tương ứng **không nằm trong RAM** (Valid bit = 0).

### 5.2 Quy trình xử lý Page Fault

```
  CPU truy cập address
        │
        ▼
  Tra Page Table     ──── Valid=1 ────▶  Truy cập bình thường
        │
     Valid=0
        │
        ▼
  ┌─ PAGE FAULT! (trap to OS) ─┐
  │                              │
  │  1. OS tìm page trên disk   │
  │  2. Tìm free frame ở RAM    │
  │     (nếu hết → chọn victim  │
  │      page để evict/swap out) │
  │  3. Load page từ disk → RAM  │
  │  4. Update page table       │
  │     (Valid=1, Frame=#)       │
  │  5. Restart instruction      │
  └──────────────────────────────┘

  Chi phí: ~1-10ms (disk I/O) = CHẬM CỰC KỲ so với cache hit (1ns)
```

### 5.3 Page Replacement Algorithms

Khi RAM đầy, OS phải chọn page nào để "đuổi ra" (evict) nhường chỗ:

| Algorithm   | Cách hoạt động                                  | Nhận xét                                         |
| ----------- | ----------------------------------------------- | ------------------------------------------------ |
| **FIFO**    | Đuổi page vào sớm nhất                          | Đơn giản nhưng không hiệu quả (Bélády's anomaly) |
| **LRU**     | Đuổi page ít dùng gần đây nhất                  | Tốt nhưng tốn chi phí tracking                   |
| **Clock**   | Xấp xỉ LRU bằng reference bit + circular buffer | Linux dùng biến thể này                          |
| **Optimal** | Đuổi page sẽ không dùng lâu nhất                | Lý thuyết — không thể implement thực tế          |

> **Liên hệ**: LRU cũng được dùng trong **Redis eviction** và **cache invalidation** — cùng nguyên lý!

### 5.4 Thrashing

Khi quá nhiều processes cạnh tranh RAM → page fault liên tục → CPU **phần lớn thời gian chờ disk I/O** thay vì tính toán. Giải pháp: thêm RAM, giảm số processes, hoặc dùng working set model.

**Follow-up Q: OOM Killer trên Linux là gì?**

> Khi RAM+swap hết, Linux kernel chọn process "nặng" nhất và **giết** nó (Out-of-Memory Killer). Tiêu chí chọn: process dùng nhiều RAM nhất, không phải root, không phải kernel. Bị OOM kill = process biến mất không warning! Trong production: set `oom_score_adj = -1000` cho critical processes (để không bị kill), limit memory với cgroups/Docker `--memory=2g`.

**Follow-up Q: Swap là gì? Nên tắt swap cho server?**

> Swap = vùng disk dùng như "RAM mở rộng". Khi RAM đầy, OS đẩy pages ra swap (disk) → chậm 1000x. **Database servers** (Redis, PostgreSQL): NÊN TẮT swap hoặc set `vm.swappiness=1`. Vì swap làm DB cực chậm và khó dự đoán — thà OOM kill còn hơn chạy với swap. Kubernetes: tắt swap (bắt buộc đến Kubernetes 1.22).

## 6. TLB — Translation Lookaside Buffer

### 6.1 Vấn đề

Mỗi memory access cần tra page table (nằm trong RAM) → thêm 1 lần RAM access → **chậm gấp đôi**.

### 6.2 TLB là gì?

TLB là **cache chuyên biệt** cho page table entries, nằm trong CPU. Thường chỉ 64-1024 entries nhưng hit rate >99%.

```
CPU cần address translation:

  Virtual Address
        │
        ▼
  ┌───────────┐
  │    TLB    │──── TLB HIT ────▶ Physical Address (nhanh, ~1ns)
  │  (cache)  │                    Không cần truy cập page table!
  └─────┬─────┘
        │
     TLB MISS
        │
        ▼
  ┌───────────┐
  │Page Table │──── Tìm thấy ──▶ Physical Address + Update TLB
  │ (in RAM)  │                   Lần sau sẽ TLB hit
  └─────┬─────┘
        │
     Page Fault
        │
        ▼
  Load from Disk (rất chậm)
```

### 6.3 TLB và Context Switch

Khi OS chuyển từ Process A sang Process B → **TLB phải FLUSH** (xóa sạch) vì page table khác nhau. Đây là một lý do context switch tốn kém.

> Một số CPU hiện đại có **ASID (Address Space ID)** trong TLB entry, cho phép giữ entries của nhiều processes → giảm chi phí context switch.

**Follow-up Q: TLB shootdown là gì? Tại sao ảnh hưởng multi-core?**

> Khi 1 core thay đổi page table (vd: `munmap`, `free`), TLB của TẤT CẢ cores khác phải invalidate entry tương ứng. Core gửi IPI (Inter-Processor Interrupt) đến các cores khác → chúng phải dừng lại, flush TLB entry, rồi tiếp tục. Với nhiều cores (32-128): đây là bottleneck. Giảm bằng: batch TLB invalidation, lazy TLB mode, PCID (Process Context ID).

**Follow-up Q: Node.js có bị ảnh hưởng TLB misses không?**

> CÓ, khi V8 heap lớn (GB). Mỗi GC cycle di chuyển objects giữa old/new space → thay đổi page mappings → TLB misses. Huge Pages giúp giảm đáng kể: `node --huge-max-old-generation-size` (Node 14+). V8 cũng tối ưu bằng cách allocate objects compact trong cùng page khi có thể.

### 7.0 Chương Trình Gồm Những Gì?

```
Trước khi hiểu memory layout, phải hiểu:
Một CHƯƠNG TRÌNH gồm các thành phần nào?

  ┌────────────────────────────────────────────────────────────┐
  │                 CẤU TRÚC CHƯƠNG TRÌNH                      │
  ├────────────────────────────────────────────────────────────┤
  │                                                            │
  │  (1) CODE                                                  │
  │      Functions, procedures, classes, methods               │
  │      → Tập INSTRUCTIONS (chỉ thị) cho CPU                 │
  │                                                            │
  │  (2) LOCAL DATA                                            │
  │      Arguments, local variables, object properties         │
  │      → Tạo ra KHI function chạy, HUỶ khi function xong   │
  │                                                            │
  │  (3) GLOBAL DATA                                           │
  │      Global variables, constants                           │
  │      → Sống SUỐT đời chương trình                         │
  │                                                            │
  │  (4) STATIC DATA                                           │
  │      String literals, static structures                    │
  │      → Biết trước SIZE, không thay đổi                    │
  │                                                            │
  └────────────────────────────────────────────────────────────┘

  → Mỗi loại cần chiến lược LƯU TRỮ khác nhau trong memory!
```

### 7.1 Functions và Stack — Tại Sao Cần Stack?

```
GIẢI PHẪU 1 FUNCTION:

  function add(a, b) {     ← nhận ARGUMENTS (input)
    const sum = a + b;     ← tạo LOCAL VARIABLE
    return sum;            ← trả KẾT QUẢ
  }                        ← SAU KHI XONG: huỷ tất cả local data!

QUY TẮC QUAN TRỌNG:
  ✅ Sau khi function hoàn thành → tất cả local data phải bị DESTROY
  ✅ Functions có thể GỌI functions khác (kể cả chính nó = recursion)

VẤN ĐỀ: Làm sao xoá memory sau khi function xong?
→ DÙNG STACK!
```

```
STACK HOẠT ĐỘNG NHƯ THẾ NÀO VỚI FUNCTIONS:

  Ví dụ: main() gọi add(3, 5), add() gọi log()

  Bước 1:               Bước 2:              Bước 3:
  main() chạy           gọi add(3,5)         add() gọi log()

  ┌──────────┐          ┌──────────┐         ┌──────────┐
  │          │          │          │         │  log()   │ ← Frame 3
  │          │          │          │         │  locals  │
  │          │          │          │         ├──────────┤
  │          │          │ add()    │         │ add()    │ ← Frame 2
  │          │          │ a=3,b=5  │         │ a=3,b=5  │
  │          │          │ sum=8    │         │ sum=8    │
  ├──────────┤          ├──────────┤         ├──────────┤
  │ main()   │          │ main()   │         │ main()   │ ← Frame 1
  │ locals   │          │ locals   │         │ locals   │
  └──────────┘          └──────────┘         └──────────┘

  Bước 4:               Bước 5:
  log() xong → POP      add() xong → POP

  ┌──────────┐          ┌──────────┐
  │          │          │          │
  │          │          │          │
  │          │          │          │
  │ add()    │          │          │
  │ a=3,b=5  │          │          │
  │ sum=8    │          │          │
  ├──────────┤          ├──────────┤
  │ main()   │          │ main()   │
  │ locals   │          │ locals   │
  └──────────┘          └──────────┘

  Mỗi function call → PUSH frame mới lên stack
  Function xong → POP frame ra → memory tự động giải phóng!

STACK FRAME chứa gì?
  ┌───────────────────────────┐
  │  Return address           │ ← quay về đâu sau khi xong
  │  Arguments (a=3, b=5)     │ ← input parameters
  │  Local variables (sum=8)  │ ← biến cục bộ
  │  Saved registers          │ ← trạng thái CPU trước đó
  └───────────────────────────┘

TẠI SAO STACK CỰC NHANH?
  ✅ Memory là array → stack = array-based → O(1) push/pop
  ✅ Không cần "tìm" chỗ trống (chỉ di chuyển stack pointer)
  ✅ Cache-friendly (liên tục trong memory)

  ❌ NHƯNG: kích thước CỐ ĐỊNH (~1-8MB)
  ❌ Quá nhiều recursion → STACK OVERFLOW!
```

```
TRẢ DỮ LIỆU TỪ FUNCTION:

  Nếu function xoá hết local data khi xong...
  Vậy dữ liệu trong "return" đi đâu?

  → COPY BY VALUE (sao chép giá trị)!

  function getAge() {
    const age = 25;    // local variable trên stack
    return age;        // COPY bits của 25 ra ngoài
  }

  const myAge = getAge();
  // myAge = 25 (bản COPY, không phải original)

  → Với primitives (number, boolean): sao chép NHANH (vài bytes)
  → Trong JS: primitives hoạt động chính xác như thế này
  → Nhưng nếu data LỚN (array 1 triệu phần tử)?
    → Copy quá CHẬM → cần GIẢI PHÁP KHÁC = HEAP!
```

### 7.2 Heap — Vùng Memory "Global" Của Chương Trình

```
TẠI SAO CẦN HEAP?

  Stack có 2 HẠN CHẾ QUAN TRỌNG:
    ❌ Phải biết CHÍNH XÁC kích thước data TRƯỚC khi push
    ❌ Sao chép data lớn qua stack = CỰC CHẬM

  → Cần vùng memory khác: HEAP!

  ┌────────────────────────────────────────────────────────────┐
  │  HEAP là gì?                                               │
  │                                                            │
  │  • Vùng memory "TOÀN CỤC" của chương trình               │
  │  • Data ở đây sống TOÀN CỤC (không auto-clear)            │
  │  • Kích thước KHÔNG bị giới hạn cố định                   │
  │  • Quản lý phức tạp hơn Stack nhiều                       │
  │                                                            │
  │  USE CASES:                                                │
  │  (1) Data có SIZE KHÔNG BIẾT TRƯỚC                         │
  │      const arr = [];                                       │
  │      while (hasData) arr.push(readData());                 │
  │      // Không biết arr sẽ lớn bao nhiêu!                  │
  │                                                            │
  │  (2) SHARED DATA (nhiều nơi truy cập cùng data)            │
  │      Data nằm 1 chỗ trên heap                             │
  │      → Các function khác nhau truy cập qua POINTER         │
  │      → Không cần copy!                                     │
  │                                                            │
  │      const user = { name: "Alice", age: 30 };              │
  │      // user object NẰM TRÊN HEAP                          │
  │      // biến "user" trên STACK chỉ là POINTER trỏ tới     │
  │      updateName(user);  // truyền pointer, KHÔNG copy obj  │
  └────────────────────────────────────────────────────────────┘
```

### 7.3 Memory Layout Tổng Hợp

```
Process Memory Layout (Virtual Address Space):

  High Address  ┌──────────────────────────┐
                │       STACK              │  ▼ grows downward
                │ (function frames,        │  Tự động quản lý (LIFO)
                │  local vars, arguments,  │  Giới hạn (~1-8MB)
                │  return addresses)       │  CỰC NHANH
                ├──────────────────────────┤
                │         ↓                │
                │    (free space)          │  ← Stack và Heap
                │         ↑                │    mọc về NHAU
                ├──────────────────────────┤
                │       HEAP               │  ▲ grows upward
                │ (dynamic allocation,     │  Manual/GC quản lý
                │  objects, arrays,        │  Lớn (~GB)
                │  shared data)            │  CHẬM hơn Stack
                ├──────────────────────────┤
                │       BSS                │  Uninitialized globals
                ├──────────────────────────┤
                │       DATA               │  Initialized globals
                │   (Static Memory Area)   │  String literals,
                │                          │  constants bất biến
                ├──────────────────────────┤
                │       TEXT (Code)         │  Machine instructions
  Low Address   └──────────────────────────┘

  STATIC MEMORY AREA (trong DATA segment):
    → Dùng cho data TOÀN CỤC, KHÔNG ĐỔI, BIẾT TRƯỚC SIZE
    → Ví dụ: string literals ("hello"), constants
    → Để trên stack → lãng phí (mỗi frame copy lại)
    → Để trên heap → không cần vì size biết trước
    → Nên có segment riêng = hiệu quả nhất!
```

| Đặc điểm       | Stack                            | Heap                           | Static              |
| -------------- | -------------------------------- | ------------------------------ | ------------------- |
| **Quản lý**    | Tự động (compiler)               | Manual (`malloc/free`) hoặc GC | Compiler            |
| **Tốc độ**     | CỰC NHANH (chỉ di chuyển SP)     | Chậm hơn (fragmentation, GC)   | Nhanh (fixed addr)  |
| **Kích thước** | Nhỏ (1-8MB)                      | Lớn (GB)                       | Nhỏ, cố định        |
| **Lifetime**   | Theo function scope              | Đến khi free/GC                | Suốt đời program    |
| **Lưu gì**     | Biến local, tham số, return addr | Objects, arrays, closures      | Literals, constants |
| **Thread**     | Mỗi thread có stack **RIÊNG**    | **SHARED** giữa tất cả threads | Shared, read-only   |

```
  → Quyền truy cập: process A KHÔNG THỂ đọc memory process B
```

### 7.5 Quản Lý Heap — 5 Chiến Lược GC

```
Heap KHÔNG tự dọn dẹp như Stack!
→ Cần CƠ CHẾ để giải phóng memory không còn dùng.
→ Có 5 cách tiếp cận chính:

╔══════════════════════════════════════════════════════════════════════╗
║  CHIẾN LƯỢC 1: MANUAL MANAGEMENT (Quản lý thủ công)                ║
║  Ngôn ngữ: Assembly, C, C++                                        ║
╠══════════════════════════════════════════════════════════════════════╣
║                                                                      ║
║  Dùng allocators: malloc() / free() trong C                          ║
║                   new / delete trong C++                             ║
║                                                                      ║
║  char* str = (char*)malloc(100);  // cấp 100 bytes trên heap       ║
║  strcpy(str, "hello");                                              ║
║  free(str);                       // developer TỰ giải phóng       ║
║                                                                      ║
║  ✅ CỰC NHANH (không overhead GC)                                  ║
║  ❌ CỰC DỄ SAI:                                                    ║
║     • Use-after-free (dùng sau khi đã free → crash)                 ║
║     • Double free (free 2 lần → crash)                              ║
║     • Memory leak (quên free → memory dần hết)                      ║
║     • Dangling pointer (pointer trỏ vào vùng đã free)              ║
║                                                                      ║
╚══════════════════════════════════════════════════════════════════════╝

╔══════════════════════════════════════════════════════════════════════╗
║  CHIẾN LƯỢC 2: REFERENCE COUNTING (Đếm tham chiếu)                 ║
║  Ngôn ngữ: C++ (smart pointers), Objective-C, Swift, Rust          ║
╠══════════════════════════════════════════════════════════════════════╣
║                                                                      ║
║  Mỗi object có COUNTER: bao nhiêu biến đang trỏ tới nó?            ║
║  Khi counter = 0 → tự động XOÁ!                                    ║
║                                                                      ║
║  let a = { x: 1 };   // refCount = 1                                ║
║  let b = a;           // refCount = 2 (b cũng trỏ tới object)      ║
║  a = null;            // refCount = 1                                ║
║  b = null;            // refCount = 0 → object bị XOÁ!             ║
║                                                                      ║
║  ✅ Đơn giản, chi phí thấp                                         ║
║  ✅ Giải phóng NGAY khi counter = 0 (deterministic)                ║
║  ❌ BUG CIRCULAR REFERENCE:                                         ║
║     let a = {};  let b = {};                                        ║
║     a.ref = b;   b.ref = a;     // trỏ vào NHAU!                   ║
║     a = null;    b = null;      // refCount = 1, KHÔNG BAO GIỜ = 0 ║
║     // → MEMORY LEAK! Hai objects giữ nhau sống mãi.               ║
║                                                                      ║
╚══════════════════════════════════════════════════════════════════════╝

╔══════════════════════════════════════════════════════════════════════╗
║  CHIẾN LƯỢC 3: GC + REFERENCE COUNTING (Kết hợp)                   ║
║  Ngôn ngữ: Python, PHP, Perl                                       ║
╠══════════════════════════════════════════════════════════════════════╣
║                                                                      ║
║  Dùng RefCounting + GC phụ để phát hiện circular references         ║
║  → Giải quyết nhược điểm chính của pure RefCounting                ║
║                                                                      ║
║  ✅ Deterministic cleanup (ngay khi refCount=0)                     ║
║  ✅ Phát hiện được circular references                              ║
║  ❌ Chi phí refCount overhead + GC cycle detection                  ║
║                                                                      ║
╚══════════════════════════════════════════════════════════════════════╝

╔══════════════════════════════════════════════════════════════════════╗
║  CHIẾN LƯỢC 4: MARK & SWEEP GC                                      ║
║  Ngôn ngữ: Java, JavaScript (V8), Go                               ║
╠══════════════════════════════════════════════════════════════════════╣
║                                                                      ║
║  Hoạt động:                                                          ║
║  1. MARK: Đi từ root objects, đánh dấu mọi object "reachable"      ║
║  2. SWEEP: Xoá tất cả objects KHÔNG được đánh dấu                  ║
║  3. COMPACT (optional): Dồn objects lại để giảm fragmentation       ║
║                                                                      ║
║     Root objects          Heap memory                                ║
║     (global, stack)                                                  ║
║         │                ┌───┬───┬───┬───┬───┬───┐                  ║
║         ├──► obj A ─────►│ A │ B │ C │ D │ E │ F │                  ║
║         │    │           └───┴───┴───┴───┴───┴───┘                  ║
║         │    └──► obj B                                              ║
║         │                                                            ║
║         └──► obj D       Mark: A✓ B✓ D✓                             ║
║              │           Sweep: xoá C, E, F (unreachable)           ║
║              └──► (nil)                                              ║
║                                                                      ║
║  ✅ Giải quyết circular references (không reachable → bị xoá)      ║
║  ✅ Developer không cần quản lý memory                              ║
║  ❌ Chi phí CAO (phải scan toàn bộ heap)                            ║
║  ❌ STOP-THE-WORLD pauses (phải dừng execution để GC)               ║
║  ❌ Không deterministic (không biết KHI NÀO object bị xoá)         ║
║                                                                      ║
║  V8 (JS): dùng Generational GC + Incremental Marking               ║
║           + Concurrent Sweeping để GIẢM pause time                  ║
║                                                                      ║
╚══════════════════════════════════════════════════════════════════════╝

╔══════════════════════════════════════════════════════════════════════╗
║  CHIẾN LƯỢC 5: COMPILER-LEVEL MANAGEMENT                            ║
║  Ngôn ngữ: Rust                                                     ║
╠══════════════════════════════════════════════════════════════════════╣
║                                                                      ║
║  Tư tưởng: Compiler KIỂM TRA memory safety tại COMPILE TIME        ║
║  → Không cần GC runtime!                                            ║
║  → Nhanh như Manual (C/C++), an toàn như GC (Java/JS)!              ║
║                                                                      ║
║  Rust's Ownership System:                                            ║
║    • Mỗi value có đúng 1 OWNER                                     ║
║    • Khi owner ra khỏi scope → value tự động DROP                  ║
║    • Borrowing rules: &T (immutable ref) hoặc &mut T (1 mutable)   ║
║                                                                      ║
║  ✅ Tốc độ ngang C/C++ (zero-cost abstractions)                    ║
║  ✅ An toàn ngang GC languages (compiler guarantee)                 ║
║  ❌ Ngôn ngữ CỰC KỲ KHÓ học                                      ║
║  ❌ Development time chậm hơn (phải "chiến đấu" với compiler)      ║
║                                                                      ║
╚══════════════════════════════════════════════════════════════════════╝
```


**Follow-up Q: Stack Overflow xảy ra thế nào trong Node.js?**

> Khi call stack vượt giới hạn (~1MB default). Thường do recursion không có base case: `function f() { f(); }` → `RangeError: Maximum call stack size exceeded`. Fix: chuyển recursion thành iteration, hoặc dùng `setImmediate()` / `process.nextTick()` để "break" stack giữa các calls. Tail call optimization (TCO) chưa hoàn toàn hỗ trợ trong V8.

**Follow-up Q: Heap fragmentation là gì?**

> Sau nhiều lần alloc/free, heap có nhiều "lỗ hổng" nhỏ rải rác. Tổng free space đủ nhưng không có khối liên tục đủ lớn → allocation thất bại dù còn memory. V8 giải quyết bằng **Mark-Sweep-Compact** GC: compact objects lại liên tục, loại bỏ fragmentation. C/C++ không có compaction → fragmentation là vấn đề lớn (lý do dùng memory pools, jemalloc).

## 8. Liên Hệ Với Node.js

### 8.1 V8 Memory Structure

```javascript
// V8 chia Heap thành các vùng:
//
// ┌─────────────────────────────────────────────┐
// │  New Space (Young Generation)  ~1-8MB       │  ← new objects
// │  ├── Semi-space From                        │
// │  └── Semi-space To                          │  Scavenger GC (fast, frequent)
// ├─────────────────────────────────────────────┤
// │  Old Space (Old Generation)    ~hundreds MB │  ← survived objects
// │                                             │  Mark-Sweep-Compact GC
// ├─────────────────────────────────────────────┤
// │  Large Object Space                         │  ← objects > 256KB
// ├─────────────────────────────────────────────┤
// │  Code Space                                 │  ← JIT compiled code
// └─────────────────────────────────────────────┘
```

### 8.2 Memory Limits & Monitoring

```javascript
// V8 default heap limit:
//   64-bit: ~1.5GB (có thể tăng bằng --max-old-space-size)
//   node --max-old-space-size=4096 app.js  (set 4GB)

// Kiểm tra memory usage:
const mem = process.memoryUsage();
console.log({
  rss: `${(mem.rss / 1024 / 1024).toFixed(1)} MB`, // Resident Set Size
  heapTotal: `${(mem.heapTotal / 1024 / 1024).toFixed(1)} MB`, // Heap allocated
  heapUsed: `${(mem.heapUsed / 1024 / 1024).toFixed(1)} MB`, // Heap actually used
  external: `${(mem.external / 1024 / 1024).toFixed(1)} MB`, // C++ objects (Buffers)
});
// rss: tổng physical memory process dùng (bao gồm code, stack, heap, shared libs)
// heapUsed < heapTotal (free space trong heap)
// external: Buffer, TypedArray (allocated bởi C++, ngoài V8 heap)
```

### 8.3 Memory Leak phổ biến trong Node.js

```javascript
// 1. Global array tích lũy
const cache = [];
app.get("/data", (req, res) => {
  const data = heavyComputation();
  cache.push(data); // ← LEAK: cache lớn dần, không bao giờ xóa
  res.json(data);
});

// 2. Closures giữ reference
function createHandler() {
  const hugeData = Buffer.alloc(100 * 1024 * 1024); // 100MB
  return (req, res) => {
    // hugeData bị closure "giữ" → GC không thể thu hồi
    res.json({ size: hugeData.length });
  };
}

// 3. EventEmitter listeners không remove
const emitter = new EventEmitter();
setInterval(() => {
  emitter.on("data", (d) => console.log(d)); // thêm listener mỗi interval!
}, 1000);
// → MaxListenersExceededWarning → memory leak
```

**Follow-up Q: V8 Garbage Collector hoạt động thế nào?**

> V8 dùng **Generational GC**: **(1) Scavenger** (Minor GC): chạy trên New Space (~1-8MB), copy surviving objects giữa 2 semi-spaces (from→to), cực nhanh (~1-5ms). **(2) Mark-Sweep-Compact** (Major GC): chạy trên Old Space (GB), mark reachable objects → sweep dead → compact. Chậm hơn (~50-200ms), có thể gây pause! V8 dùng **incremental marking** + **concurrent sweeping** để giảm pause time.

**Follow-up Q: Tìm memory leak trong production Node.js?**

> **(1)** Monitor `process.memoryUsage().heapUsed` — nếu tăng liên tục theo thời gian = leak. **(2)** `node --inspect` + Chrome DevTools → Memory tab → Heap Snapshot → so sánh 2 snapshots → tìm objects tăng. **(3)** `clinic.js` (npm) — tự động phát hiện memory/event loop issues. **(4)** Production: `--heapsnapshot-signal=SIGUSR2` → gửi signal để dump heap snapshot không cần restart.

## 9. Câu Hỏi Phỏng Vấn

---

#### Q1: Giải thích Virtual Memory hoạt động ra sao.

```
╔══════════════════════════════════════════════════════════════╗
║          VIRTUAL MEMORY — TÓM TẮT FLOW                   ║
╠══════════════════════════════════════════════════════════════╣
║                                                              ║
║  Process gửi virtual address → MMU                          ║
║       │                                                      ║
║       ▼                                                      ║
║  TLB hit? ─── YES ───► Physical address (~1ns)              ║
║       │                                                      ║
║      NO                                                       ║
║       │                                                      ║
║       ▼                                                      ║
║  Page Table walk ── Found ──► Physical addr + update TLB     ║
║       │                      (~100-400ns)                     ║
║    Not in RAM                                                  ║
║       │                                                      ║
║       ▼                                                      ║
║  PAGE FAULT → OS loads from disk (~1-10ms)                   ║
║  → Update page table + TLB → Restart                        ║
║                                                              ║
╚══════════════════════════════════════════════════════════════╝
```

**Trả lời chi tiết**: Virtual Memory cho mỗi process không gian địa chỉ ảo riêng biệt. OS dùng Page Table để ánh xạ virtual → physical addresses. MMU (hardware) tra TLB trước (≈cache của page table), nếu miss thì walk page table trong RAM. Nếu page không có trong RAM → page fault → load từ disk. 3 lợi ích: (1) isolation, (2) abstraction, (3) overcommit.

**Follow-up Q: Overcommit trong Linux là gì?**

> Linux cho phép `malloc()` thành công dù không đủ physical RAM (đây là overcommit). Physical pages chỉ được allocate khi THỰC SỰ GHI vào (demand paging). Lợi ích: processes dùng ít memory hơn đã allocate. Nguy hiểm: nếu tất cả processes ghi cùng lúc → hết RAM → OOM Killer. Control: `vm.overcommit_memory` (0=heuristic, 1=always, 2=never).

---

#### Q2: Page fault ảnh hưởng performance thế nào?

> Chi phí: ~1-10ms (disk I/O) so với normal access ~100ns → chậm hơn **100,000 lần**. Ví dụ thực tế: Node.js process dùng 2GB heap trên server 1GB RAM → page faults liên tục → response time từ 5ms → 500ms+. Giải pháp: **(1)** Thêm RAM (rẻ nhất!), **(2)** Giảm working set (tối ưu memory usage), **(3)** Tắt swap (cho server), **(4)** Dùng `mlockall()` để pin pages trong RAM (cho critical services).

**Follow-up Q: Minor vs Major page fault?**

> **Minor**: page chưa được map trong page table nhưng không cần disk I/O (vd: first access to mmap'd file đã có trong page cache, hoặc demand-zeroed page). Chỉ tốn ~1-10μs. **Major**: phải đọc từ disk → đắt gnấp 1000x. Monitor: `ps -o min_flt,maj_flt` hoặc `sar -B`. Nhiều major faults = CẦN THÊM RAM.

**Follow-up Q: WeakMap/WeakRef giúp gì?**

> `WeakMap`: keys là weak references — nếu không có reference khác đến key, GC tự thu hồi cả key + value. Dùng cho: caching objects mà không ngăn GC. `WeakRef` (ES2021): giữ weak reference đến object, `.deref()` có thể trả `undefined` nếu đã bị GC. Dùng cho: cache mà không gây leak, kết hợp `FinalizationRegistry` để cleanup.

#### Q4: Stack vs Heap — data nào lưu ở đâu trong JavaScript?

> **Stack**: primitives (numbers, strings nhỏ, booleans, undefined, null), function frames (return address, arguments). **Heap**: objects, arrays, functions, closures, strings lớn. V8 đặc biệt: SMI (Small Integers, -2³¹ đến 2³¹-1) lưu trực tiếp trong pointer (tagged pointer) — không cần heap allocation! Đây là lý do integer math nhanh hơn float trong V8.

**Follow-up Q: JavaScript variables lưu ở stack hay heap?**

> `let x = 42` — 42 (SMI) có thể nằm trên stack. `let obj = {a: 1}` — obj (pointer) trên stack, nhưng object `{a:1}` trên HEAP. `const arr = [1,2,3]` — arr (pointer) trên stack, array trên HEAP. Closures phức tạp hơn: biến captured bởi closure được move từ stack lên heap ("escape analysis"). V8 tối ưu: nếu biết biến KHÔNG escape, giữ trên stack (stack allocation = nhanh hơn).
