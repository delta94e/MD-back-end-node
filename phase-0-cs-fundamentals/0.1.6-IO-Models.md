## 1. Bốn Mô Hình I/O

Khi process gọi `read()` trên socket/file, có hai giai đoạn:

1. **Chờ data sẵn sàng** (data từ network/disk đến kernel buffer)
2. **Copy data** từ kernel buffer → user buffer

Dựa vào hành vi ở 2 giai đoạn này, có 4 mô hình I/O:

```
                         Wait for data    Copy data
                         ──────────────   ──────────
Blocking I/O:            Block            Block        ← đơn giản nhất
Non-blocking I/O:        Return immediately (poll)  Block
I/O Multiplexing:        Block on select/epoll      Block
Async I/O (AIO):         Non-block         Non-block  ← notify khi xong
```

## 2. Blocking I/O

```
Application                        Kernel
    │                                 │
    │  read(socket, buf)              │
    │ ──────────────────────────────▶ │
    │                                 │  Chờ data đến...
    │       BLOCKED!                  │  (network packet,
    │   (thread ngủ,                  │   disk sector)
    │    không làm gì)                │
    │                                 │  Data đến!
    │                                 │  Copy kernel→user
    │ ◀────────────────────────────── │
    │  return data                    │
    │                                 │
    ▼  Tiếp tục xử lý                │
```

**Đặc điểm**:

- Thread bị **block hoàn toàn** cho đến khi I/O hoàn tất
- Mỗi client cần **1 thread riêng** → C10K problem (10,000 clients = 10,000 threads)
- Thread tốn ~1MB stack memory + context switch overhead

```javascript
// Node.js: fs.*Sync() là blocking I/O
const data = fs.readFileSync("/data/big-file.txt"); // Thread ngủ ở đây!
// Không gì khác được xử lý cho đến khi đọc xong
console.log("Done"); // Chỉ chạy sau khi file đọc xong
```

**Mô hình server**: Thread-per-connection (Java Servlet truyền thống, PHP-FPM)

```
Client 1 ──▶ Thread 1 ──▶ read(DB)... block... return... respond
Client 2 ──▶ Thread 2 ──▶ read(DB)... block... return... respond
Client 3 ──▶ Thread 3 ──▶ read(DB)... block... return... respond
...
Client 1000 ──▶ Thread 1000 (1GB memory cho stacks!)
```

## 3. Non-blocking I/O

```
Application                        Kernel
    │                                 │
    │  read(socket, buf, O_NONBLOCK)  │
    │ ──────────────────────────────▶ │
    │ ◀─── EWOULDBLOCK (not ready)   │  (chưa có data)
    │                                 │
    │  ... làm việc khác ...          │
    │                                 │
    │  read(socket, buf, O_NONBLOCK)  │  POLLING
    │ ──────────────────────────────▶ │
    │ ◀─── EWOULDBLOCK (not ready)   │  (vẫn chưa)
    │                                 │
    │  read(socket, buf, O_NONBLOCK)  │
    │ ──────────────────────────────▶ │
    │ ◀─── data!                      │  Data đến! Copy và return
    │                                 │
    ▼  Xử lý data                    │
```

**Đặc điểm**:

- Thread **không bị block** — nhận `EWOULDBLOCK` ngay nếu chưa có data
- Cần **polling liên tục** (busy-waiting) → lãng phí CPU
- Không thực dụng khi dùng đơn lẻ → kết hợp với I/O multiplexing

## 4. I/O Multiplexing — select, poll, epoll

> 💡 Ý tưởng: **Một thread** giám sát **nhiều fd** cùng lúc. Khi bất kỳ fd nào ready → xử lý.

```
Application                              Kernel
    │                                      │
    │  epoll_wait(fds=[sock1,sock2,...])    │
    │ ────────────────────────────────────▶ │
    │                                      │  Giám sát tất cả sockets...
    │       BLOCKED on epoll               │
    │   (nhưng giám sát NHIỀU fd           │
    │    cùng lúc!)                         │
    │                                      │  sock3 có data!
    │ ◀──── sock3 ready!                   │
    │                                      │
    │  read(sock3, buf)                    │
    │ ────────────────────────────────────▶ │
    │ ◀──── data                           │  Copy data
    │                                      │
    │  process(data)                       │
    │  epoll_wait(...)  // tiếp tục         │
```

**Đây chính là cách Node.js hoạt động!** — libuv dùng `epoll` (Linux) / `kqueue` (macOS) / `IOCP` (Windows).

## 5. Asynchronous I/O (AIO)

```
Application                        Kernel
    │                                 │
    │  aio_read(socket, buf, callback)│
    │ ──────────────────────────────▶ │
    │ ◀─── OK (submitted)            │  (return ngay lập tức)
    │                                 │
    │  ... làm việc khác ...          │  Kernel đọc data...
    │  ... hoàn toàn free ...         │  Copy data...
    │                                 │
    │ ◀─── SIGNAL: data ready!        │  Notify khi hoàn tất
    │                                 │
    ▼  Xử lý data trong callback      │
```

**Đặc điểm**: Hoàn toàn non-blocking ở cả 2 giai đoạn. Linux AIO (`io_uring` từ kernel 5.1+) hỗ trợ true async I/O.

> **Node.js**: Dù API `fs.readFile()` trông "async", thực tế nó dùng **thread pool** (libuv) + blocking read ở worker thread, KHÔNG phải kernel AIO. Network I/O mới dùng epoll thật sự non-blocking.

## 6. So Sánh Tổng Hợp

| Mô hình           | Wait            | Copy      | Thread cần    | Performance         |
| ----------------- | --------------- | --------- | ------------- | ------------------- |
| **Blocking**      | Block           | Block     | 1/client      | O(n) threads        |
| **Non-blocking**  | Return (poll)   | Block     | 1 (busy loop) | CPU waste           |
| **I/O Multiplex** | Block on select | Block     | 1 cho tất cả  | ✅ Scalable         |
| **Async I/O**     | Non-block       | Non-block | 1 cho tất cả  | ✅ Best (lý thuyết) |

## 7. epoll vs select vs poll — Chi Tiết

### 7.1 select

```c
// Pseudocode
fd_set read_fds;
FD_SET(sock1, &read_fds);
FD_SET(sock2, &read_fds);
FD_SET(sock3, &read_fds);

select(max_fd + 1, &read_fds, NULL, NULL, timeout);
// Returns: số fd ready

// Phải loop qua TẤT CẢ fd để tìm fd nào ready
for (int fd = 0; fd <= max_fd; fd++) {
  if (FD_ISSET(fd, &read_fds)) {
    // fd ready → xử lý
  }
}
```

**Nhược điểm**:

- Giới hạn **FD_SETSIZE = 1024** fd
- Mỗi lần gọi phải **copy toàn bộ fd_set** từ user space → kernel space
- Return → phải **scan toàn bộ** O(n) để tìm fd ready
- Mỗi lần gọi lại phải **khởi tạo lại** fd_set

### 7.2 poll

```c
struct pollfd fds[3];
fds[0] = { .fd = sock1, .events = POLLIN };
fds[1] = { .fd = sock2, .events = POLLIN };
fds[2] = { .fd = sock3, .events = POLLIN };

poll(fds, 3, timeout);
// Không giới hạn số fd (dùng array thay vì bitmap)
// Nhưng vẫn O(n) scan mỗi lần gọi
```

**Cải thiện**: Không có giới hạn 1024. Nhưng vẫn O(n) scan.

### 7.3 epoll (Linux) / kqueue (macOS)

```c
// 1. Tạo epoll instance (chỉ 1 lần)
int epfd = epoll_create(1);

// 2. Đăng ký fd quan tâm (chỉ khi có fd mới)
struct epoll_event ev = { .events = EPOLLIN, .data.fd = sock1 };
epoll_ctl(epfd, EPOLL_CTL_ADD, sock1, &ev);  // thêm sock1
epoll_ctl(epfd, EPOLL_CTL_ADD, sock2, &ev);  // thêm sock2

// 3. Chờ events (gọi lặp lại)
struct epoll_event events[MAX_EVENTS];
int n = epoll_wait(epfd, events, MAX_EVENTS, timeout);

// CHỈ trả về fd READY — không cần scan O(n)!
for (int i = 0; i < n; i++) {
  handle(events[i].data.fd);  // Chỉ xử lý fd ready
}
```

### 7.4 So sánh hiệu năng

|                          | select       | poll          | epoll/kqueue                |
| ------------------------ | ------------ | ------------- | --------------------------- |
| Max fd                   | 1024         | Unlimited     | Unlimited                   |
| Mỗi lần gọi              | Copy all fds | Copy all fds  | Không copy (kernel track)   |
| Tìm fd ready             | O(n) scan    | O(n) scan     | O(1) — chỉ return ready fds |
| fd thêm/xóa              | Rebuild set  | Rebuild array | `epoll_ctl` — incremental   |
| **10,000 fds, 10 ready** | Scan 10,000  | Scan 10,000   | **Return 10**               |

> **Kết luận**: Với 10,000+ connections, `epoll` nhanh hơn `select/poll` hàng trăm lần vì O(active) thay vì O(total).

## 8. Liên Hệ Trực Tiếp Với Node.js Event Loop

### Kiến trúc Node.js I/O

```
┌──────────────────────────────────────────────────────────┐
│                       Node.js                             │
│                                                           │
│  ┌──────────────────┐                                    │
│  │  V8 Engine       │  JavaScript execution              │
│  │  (Call Stack)     │                                    │
│  └────────┬─────────┘                                    │
│           │                                               │
│  ┌────────▼─────────────────────────────────────────┐    │
│  │              libuv Event Loop                      │    │
│  │                                                    │    │
│  │  Network I/O:    epoll/kqueue (kernel) ── NO threads│    │
│  │  File I/O:       Thread Pool (4 threads) ── blocking│    │
│  │  DNS lookup:     Thread Pool                        │    │
│  │  Crypto/Zlib:    Thread Pool                        │    │
│  └────────────────────────────────────────────────────┘    │
│                                                           │
│  Khi epoll_wait return "socket ready":                    │
│    → libuv đọc data                                      │
│    → tạo callback                                         │
│    → đẩy vào Event Loop queue                             │
│    → V8 call stack rảnh → pick callback → execute         │
│                                                           │
└──────────────────────────────────────────────────────────┘
```

### Tại sao Node.js handle 10,000+ concurrent connections trên 1 thread?

```
Câu trả lời đầy đủ:

1. Network I/O dùng epoll (Linux) / kqueue (macOS):
   - KHÔNG tạo thread cho mỗi connection
   - 1 epoll instance giám sát hàng nghìn sockets
   - epoll_wait block cho đến khi ≥1 socket ready
   - Chỉ xử lý sockets CÓ data → O(active), không O(total)

2. Mỗi request xử lý rất nhanh (non-CPU-bound):
   - Parse request (~μs)
   - Gửi DB query (async, non-blocking)
   - Gửi response khi DB callback (~μs)
   - Tổng CPU time per request: < 1ms

3. Nếu 10,000 connections, mỗi request 0.1ms CPU:
   - 1 thread xử lý: 10,000 × 0.1ms = 1 second
   - Throughput: ~10,000 RPS trên SINGLE THREAD

4. File I/O và crypto dùng thread pool (default 4 threads)
   vì OS APIs cho file thường blocking.
   → UV_THREADPOOL_SIZE=128 nếu heavy file I/O
```

### Code demo: epoll-style thinking in Node.js

```javascript
const http = require("http");

// Node.js tương đương với:
// while (true) {
//   events = epoll_wait(eventfd); // chờ socket ready
//   for (event of events) {
//     if (event == new_connection) accept();
//     if (event == data_ready) handleRequest();
//     if (event == write_ready) sendResponse();
//   }
// }

const server = http.createServer((req, res) => {
  // Callback này chạy khi epoll báo "socket có data"
  // Xử lý nhanh (non-blocking) → return → tiếp tục epoll_wait
  res.end("Hello");
});

server.listen(3000);
// Bên dưới: libuv gọi epoll_create → bind socket → epoll_wait loop
```

## 9. Câu Hỏi Phỏng Vấn

**Q: `epoll` khác `select` và `poll` ra sao? Tại sao `epoll` hiệu quả hơn ở scale lớn?**

> A: `select` giới hạn 1024 fds, mỗi lần gọi copy toàn bộ fd_set vào kernel và phải O(n) scan để tìm fd ready. `poll` bỏ giới hạn 1024 nhưng vẫn O(n) scan. `epoll` dùng cách tiếp cận khác: (1) đăng ký fd một lần bằng `epoll_ctl`, kernel tự track; (2) `epoll_wait` CHỈ trả về danh sách fd ready, không cần scan → O(active) thay vì O(total). Với 10,000 connections nhưng chỉ 10 active, select scan 10,000 còn epoll chỉ return 10.

**Q: Liên hệ epoll với Event Loop của Node.js?**

> A: libuv (engine bên dưới Node.js) dùng epoll (Linux) / kqueue (macOS) / IOCP (Windows) cho network I/O. Event loop gọi `epoll_wait` → nhận danh sách sockets ready → đọc data → tạo callbacks → đẩy vào event queue → V8 thực thi. Vì mỗi callback xử lý nhanh (microseconds), 1 thread đủ handle tens of thousands connections. File I/O dùng thread pool vì `read()` syscall là blocking.

**Q: Blocking vs Non-blocking vs Async — phân biệt rõ ràng?**

> A: **Blocking**: thread ngủ cho đến khi I/O hoàn tất. **Non-blocking**: system call return ngay (EWOULDBLOCK nếu chưa ready), nhưng khi data copy vẫn block. **Async**: hoàn toàn non-blocking — kernel thực hiện cả chờ + copy, notify khi xong. Trong Node.js: network I/O = non-blocking + epoll (gần async), file I/O = blocking trên thread pool worker (giả async — vì từ góc nhìn main thread, nó non-blocking).

## 10. CS Frontend: Async Programming, Callbacks & Event Source

> 📺 Nguồn: CS Frontend — Asynchronous Programming, Callbacks, Event Source Pattern

### 10.1 Sequential vs Event-Driven Execution

```
SEQUENTIAL (tuần tự) — normal program flow:

  instruction 1  →  instruction 2  →  instruction 3
  → Đọc code = BIẾT CHẮC thứ tự thực thi
  → Đơn giản, predictable

NHƯNG: có những việc PHẢI CHỜ EVENT!

  ┌──────────────────────────────────────────────────┐
  │  Ví dụ các events KHÔNG THỂ dự đoán thời gian:  │
  │                                                  │
  │  → User click button (khi nào click?)            │
  │  → Server trả response (mất bao lâu?)           │
  │  → CPU rảnh (idle callback)                      │
  │  → Timer hết hạn                                 │
  │  → File đọc xong                                 │
  └──────────────────────────────────────────────────┘

  → Thời gian trigger = KHÔNG DỰ ĐOÁN ĐƯỢC!
  → Code PHẢI CHỜ event xảy ra!
  → Nhưng chờ KIỂU GÌ?
```

### 10.2 Thread Sleeping & Supervisor

```
CÁCH 1: ĐẶT THREAD NGỦ (Thread Sleeping)

  ┌─────────────────────────────────────────────────┐
  │  code...                                        │
  │  ↓                                               │
  │  ASYNC OPERATION (gửi request đến server)        │
  │  ↓                                               │
  │  Thread NGỦ 💤 (block, không làm gì)             │
  │  ↓                                               │
  │  ... chờ ... chờ ... chờ ...                     │
  │  ↓                                               │
  │  SUPERVISOR đánh thức thread! (data đến!)        │
  │  ↓                                               │
  │  Tiếp tục xử lý data                            │
  └─────────────────────────────────────────────────┘

  SUPERVISOR = thực thể BÊN NGOÀI đánh thức thread:
  → Browser, OS, runtime environment
  → Thread KHÔNG THỂ tự thức dậy!
  → Supervisor biết KHI NÀO event xảy ra (dùng OS API)
```

### 10.3 Synchronous Blocking — Ví Dụ

```javascript
// SYNCHRONOUS (blocking) XMLHttpRequest:
function getUserData(id) {
  var request = new XMLHttpRequest();
  request.open("GET", `/user/${id}`, false); // false = SYNCHRONOUS!
  request.send(null); // ← THREAD NGỦ Ở ĐÂY!

  if (request.status === 200) {
    return request.response;
  }
}

console.log(1); // → in "1"
console.log(getUserData("10")); // → THREAD NGỦ... chờ server...
//   server trả về → in data
console.log(2); // → in "2"

// OUTPUT: 1 → [data] → 2 (tuần tự, BLOCKING)
```

```
❌ VẤN ĐỀ VỚI BLOCKING:

  timeline:
  ────────────────────────────────────────────────
  log(1)  │  getUserData()  │  BLOCKED!  │  log(2)
  0ms     │  1ms            │  500ms     │  501ms
                               ↑
                          Thread NGỦ ở đây!
                          UI ĐÓNG BĂNG!
                          User nghĩ site bị CRASH!

  → Block main thread = block TOÀN BỘ UI!
  → Không scroll, click, type... được
  → User experience = KINH KHỦNG!
```

### 10.5 Callbacks — Giải Pháp

```
CALLBACK = function được TRUYỀN VÀO để gọi SAU khi event xảy ra:

  ┌──────────────────────────────────────────────────────┐
  │  1. Tách code cần chạy khi event → thành FUNCTION    │
  │  2. Truyền function này cho async operation           │
  │  3. Async operation RETURN NGAY (không block!)       │
  │  4. Code tiếp theo chạy BÌNH THƯỜNG                  │
  │  5. Khi event xảy ra → supervisor GỌI callback       │
  └──────────────────────────────────────────────────────┘

  timeline (non-blocking):
  ───────────────────────────────────────────────────────
  log(1) │ getUserData() │ log(2) │    ... │ cb(data)
  0ms    │ 1ms (return!) │ 2ms    │        │ 500ms
                                             ↑
                                    supervisor gọi callback!
                                    KHÔNG block main thread!
```

```javascript
// ASYNCHRONOUS (non-blocking) XMLHttpRequest:
function getUserData(id, cb) {
  var request = new XMLHttpRequest();
  request.open("GET", `/user/${id}`, true); // true = ASYNCHRONOUS!

  request.onload = function () {
    if (request.readyState === 4 && request.status === 200) {
      cb(request.response); // ← Callback được gọi SAU khi data đến
    }
  };
  request.send(null); // ← RETURN NGAY! Không block!
}

console.log(1); // → in "1"
getUserData("10", console.log); // → gửi request, RETURN NGAY
console.log(2); // → in "2" (NGAY LẬP TỨC!)
// ... sau 500ms ...
// → callback gọi: in [data]

// OUTPUT: 1 → 2 → [data] (NON-BLOCKING!)
```

### 10.6 Macrotasks, Microtasks & Event Loop

```
SAU KHI CÓ CALLBACKS — cơ chế hoạt động:

  1. Function tạo async operation → CHẤP NHẬN callback
  2. Supervisor (browser) đặt callback vào QUEUE
  3. Async function RETURN ngay → code tiếp tục
  4. Supervisor BIẾT khi nào task hoàn thành (nhờ OS API)
  5. Khi task xong → lấy callback từ queue → thực thi

  EVENT LOOP = VÒNG LẶP VÔ HẠN của supervisor:

  ┌─────────────────────────────────────────────────────┐
  │                                                     │
```

### 10.7 Asynchronous ≠ Parallel!

```
⚠️ ASYNC ≠ PARALLEL — ĐỪNG NHẦM LẪN!

  ASYNCHRONOUS:
  → "Không chờ, làm việc khác, quay lại SAU"
  → Nói về THỜI ĐIỂM thực thi
  → Có thể xảy ra trên 1 THREAD duy nhất

  PARALLEL:
  → "Nhiều việc chạy ĐỒNG THỜI"
  → Nói về SỐ LƯỢNG threads/cores
  → Cần multiple threads/processes

  ┌──────────────────────────────────────────────────────┐
  │ Async + single thread:                               │
  │ ───[task A]───────[task B]──────[task A cont.]───    │
  │ → A dừng, B chạy, A tiếp tục (XEN KẼ, không song song)│
  │                                                      │
  │ Parallel + multi thread:                             │
  │ Thread 1: ───[task A]──────────────────              │
  │ Thread 2: ───[task B]──────────────────              │
  │ → A và B chạy CÙNG LÚC (thật sự song song)         │
  │                                                      │
  │ Async + Parallel: (Node.js network I/O)              │
  │ Main thread: ───JS code──callback───JS code───       │
  │ OS kernel:   ───network I/O════════──notify──        │
  │ → JS code async, network I/O parallel!              │
  └──────────────────────────────────────────────────────┘

  → Network requests: CÓ THỂ parallel (OS xử lý)
  → User events: KHÔNG BAO GIỜ parallel (cùng UI thread)
  → Sync code CÓ THỂ parallel (chạy trên threads khác nhau)
  → Async code CÓ THỂ sequential (1 thread)

  → ĐỪNG NHẦM 2 khái niệm này!
```

### 10.8 Event Source Pattern — on/off/emit

```
VẤN ĐỀ VỚI CALLBACKS THÔNG THƯỜNG:

  → Truyền callback qua ARGUMENTS: chỉ 1 callback
  → Gán callback vào PROPERTY: chỉ 1 handler
  → KHÔNG THỂ thêm nhiều handlers
  → Thiếu standardization

GIẢI PHÁP: EVENT SOURCE PATTERN!

  ┌──────────────────────────────────────────────────────┐
  │  3 METHODS chính (API contract):                     │
  │                                                      │
  │  on(eventName, callback)                             │
  │  → Đăng ký handler cho event                        │
  │  → CÓ THỂ đăng ký NHIỀU handlers cho 1 event!      │
  │                                                      │
  │  off(eventName, callback)                            │
  │  → Hủy đăng ký handler                              │
  │  → Cần reference đến ĐÚNG function đã đăng ký       │
  │                                                      │
  │  emit(eventName, ...args)                            │
  │  → Kích hoạt TẤT CẢ handlers của event              │
  │  → Truyền arguments cho mỗi handler                 │
  └──────────────────────────────────────────────────────┘
```

```javascript
// IMPLEMENT Event Source (EventEmitter):
class EventEmitter {
  constructor() {
    this._events = {}; // { eventName: [handler1, handler2,...] }
  }

  on(event, handler) {
    if (!this._events[event]) this._events[event] = [];
    this._events[event].push(handler);
    return this; // chainable!
  }

  off(event, handler) {
    if (!this._events[event]) return this;
    this._events[event] = this._events[event].filter((h) => h !== handler);
    return this;
  }

  emit(event, ...args) {
    if (!this._events[event]) return false;
    this._events[event].forEach((h) => h(...args));
    return true;
  }
}

// Dùng:
const emitter = new EventEmitter();

const onData = (data) => console.log("Got:", data);
const onLog = (data) => console.log("Log:", data);

emitter.on("data", onData); // handler 1
emitter.on("data", onLog); // handler 2 cho CÙNG event!

emitter.emit("data", "hello");
// → "Got: hello"
// → "Log: hello" (cả 2 handlers đều được gọi!)

emitter.off("data", onLog); // hủy handler 2
emitter.emit("data", "world");
// → "Got: world" (chỉ còn handler 1)
```

### 11.3 throw / try-catch-finally

```javascript
// THROW = cách trả về giá trị ĐẶC BIỆT từ function:
// → Kiểu trả về của throw KHÁC với return!
// → Mô tả TẤT CẢ trường hợp ngoại lệ

function divide(a, b) {
  if (b === 0) throw new Error("Division by zero!"); // exception!
  return a / b; // normal return
}

// try-catch-finally:
try {
  const result = divide(10, 0);
  console.log(result); // không chạy!
} catch (err) {
  console.error(err.message); // "Division by zero!"
} finally {
  console.log("Always runs"); // LUÔN chạy, dù có exception hay không!
}
```

```
THROW vs RETURN:

  ┌───────────────────────────────────────────────────────┐
  │                   return          throw                  │
  ├───────────────┬─────────────────┬─────────────────────┤

  → Nếu không ai catch → exception BUBBLES lên call stack
```

### 11.6 Exceptions & Async Code

```

  try {
```

```javascript
// GIẢI PHÁP 1: Node.js Error-First Callback Pattern
function readFile(path, callback) {
  fs.readFile(path, (err, data) => {
    if (err) {
      callback(err, null); // ARGUMENT ĐẦU TIÊN = error (hoặc null)
    } else {
      callback(null, data); // null = không có error
    }
  });
}

// Dùng:

  if (err) {
    // LUÔN check error trước!

    return;

});

// GIẢI PHÁP 2: EventEmitter errors
const emitter = new EventEmitter();

  console.error("Error event:", err);

// → Tốt cho macro-level error handling + delegation!
// → Quá nhiều noise cho micro-level
```

### 11.9 Option (Some / None)

```javascript
// OPTION = container cho data CÓ THỂ KHÔNG TỒN TẠI:

class Some {
  constructor(value) {
    this._value = value;
  }
  isSome() {
    return true;
  }
  isNone() {
    return false;
  }
  unwrap() {
    return this._value;
  }
  map(fn) {
    return new Some(fn(this._value));
  }
  flatMap(fn) {
    return fn(this._value);
  }
  getOrElse(_default) {
    return this._value;
  }
}

class None {
  isSome() {
    return false;
  }
  isNone() {
    return true;
  }
  unwrap() {
    throw new Error("Cannot unwrap None!");
  }
  map(_fn) {
    return this;
  } // không làm gì!
  flatMap(_fn) {
    return this;
  } // không làm gì!
  getOrElse(defaultVal) {
    return defaultVal;
  }
}

// Dùng Option thay vì null/undefined:
function findUser(id) {
  const user = db.find((u) => u.id === id);
  return user ? new Some(user) : new None();
}

const result = findUser(42);
// AN TOÀN! Không bao giờ quên check null!
const name = result
  .map((user) => user.name)
  .map((name) => name.toUpperCase())
  .getOrElse("Unknown");
// Nếu user tồn tại: "ALICE"
// Nếu không: "Unknown" (không throw, không crash!)
```

### 11.10 Result (Ok / Err)

```javascript
// RESULT = container cho operation CÓ THỂ THẤT BẠI:

class Ok {

    this._value = value;
  }
  isOk() {
    return true;
  }
  isErr() {
    return false;

    return this._value;

    return new Ok(fn(this._value));

    return this;

  }

    return false;

    return true;
```

```
  │             │                      │ Rejected             │

  │             │                      │ {done:true}          │
  │ Array       │ Nhiều giá trị        │ [] / [items...]      │
  │ Map/Set     │ Key-value / unique   │ empty / filled       │
  │ Function    │ Lazy evaluation!     │ uncalled / called    │
  └─────────────┴──────────────────────┴─────────────────────┘

  ƯĐ:
  → Không cần throw! Chỉ cần return container
  → KHÔNG THỂ "quên" xử lý error (phải dùng API của container!)
  → TypeScript: biết TYPE của container, không cần đọc code
  → Hoạt động GIỐNG NHAU cho sync và async code!

  NHƯỢC:
  → Verbose nếu không có syntactic sugar
  → Có thể tạo sugar bằng generators! ☺
```

## 12. CS Frontend: Functors, Monads & Monoids

> 📺 Nguồn: CS Frontend — Composition of Container Types. Functors, Monads, Monoids

### 12.1 Nhắc Lại — Container Types

```
CONTAINER = object CHỨA data + CONTEXT:

  → Cung cấp API để làm việc với data bên trong
  → KHÔNG cho truy cập data trực tiếp
  → Container CÓ THỂ chứa container khác (nesting!)
  → Thay thế tuyệt vời cho exceptions

  VÍ DỤ: Promise<Array<Option<User>>>
  → Promise chứa Array chứa Option chứa User
  → 3 tầng context!

  CÂU HỎI: Làm sao COMPOSE nhiều functions
  mà mỗi function trả về container?
```

### 12.2 Kleisli Arrow

```
KLEISLI ARROW = function có dạng:

  (a) → Container<b>

  → Nhận giá trị THƯỜNG (a)
  → Trả về CONTAINER chứa giá trị mới (b)

  VÍ DỤ:
  ┌─────────────────────────────────────────────────────────┐
  │  fetchUser: (id) → Promise<User>                        │
  │  writeFile: (data) → Promise<void>                      │
  │  findItem:  (name) → Option<Item>                       │
  │  parseInt:  (str) → Result<number>                      │
  └─────────────────────────────────────────────────────────┘

  VẤN ĐỀ: Làm sao CHAIN nhiều Kleisli arrows?

  fetchUser(id) → Promise<User>
  writeFile(user) → Promise<void>

  ❌ writeFile(fetchUser(id))  → SAI! fetchUser trả Promise,
                                   không phải User!
  → CẦN cách "unwrap" container → truyền value → wrap lại!
```

### 12.3 Monad — Khái Niệm

```
MONAD = container có method ĐẶC BIỆT:

  ┌─────────────────────────────────────────────────────────────┐
  │  CONTRACT:                                                  │
  │                                                             │
  │  container.bind(kleisliArrow) → container MỚI cùng type    │
  │                                                             │
  │  Hay viết dạng khác:                                       │
  │  M<a>.bind((a) → M<b>) → M<b>                              │
  │                                                             │
  │  Trong đó:                                                  │
  │  → M = loại container (Promise, Option, Result,...)        │
  │  → bind nhận Kleisli arrow: (a) → M<b>                     │
  │  → Trả về M<b> (CÙNG loại container, giá trị MỚI)         │
  │                                                             │
  │  TÊN GỌI tùy ngôn ngữ:                                     │
  │  → Haskell: >>= (bind)                                     │
  │  → JS Promise: .then()                                     │
  │  → JS Array: .flatMap()                                    │
  │  → Rust/Scala: .flat_map() / .flatMap()                    │
  └─────────────────────────────────────────────────────────────┘
```

### 12.4 Promise = Monad!

```javascript
// PROMISE LÀ MONAD — bạn đã dùng nó HÀNG NGÀY!

// Kleisli arrows:
// fetch: (url) → Promise<Response>
// response.json: () → Promise<Object>

fetch("https://api.example.com/user/100") // → Promise<Response>
  .then((response) => response.json()) // → Promise<Object>
  .then((userData) => console.log(userData)); // → Promise<void>

// MỖI .then() nhận Kleisli arrow: (a) → Promise<b>
// Trả về Promise<b> MỚI → chain TIẾP ĐƯỢC!

// COMPOSITION vô hạn:
fetch("/user/100") // Promise<Response>
  .then((res) => res.json()) // Promise<User>
  .then((user) => fetch(`/posts/${user.id}`)) // Promise<Response>
  .then((res) => res.json()) // Promise<Post[]>
  .then((posts) => posts.length); // Promise<number>
// → 5 bước, mỗi bước = Kleisli arrow, chain MỘT CHUỖI!
```

```
TẠI SAO PROMISE LÀ MONAD?

  Promise<a>.then((a) → Promise<b>) → Promise<b>  ✅

  then() nhận Kleisli arrow → trả Promise MỚI
  → ĐÚNG contract của monad!

  ┌─────────────────────────────────────────────────────┐
  │  Promise<Response>                                  │
  │    │                                                │
  │    ├─ .then(res → res.json())                      │
  │    │  → unwrap Response → gọi json()               │
  │    │  → wrap lại thành Promise<Object>               │
  │    │                                                │
  │    ├─ .then(obj → fetch(obj.url))                   │
  │    │  → unwrap Object → gọi fetch()                │
  │    │  → wrap lại thành Promise<Response>              │
  │    │                                                │
  │    └─ ... chain TIẾP vô hạn!                       │
  └─────────────────────────────────────────────────────┘
```

### 12.5 Array = Monad!

```javascript
// ARRAY CŨNG LÀ MONAD — qua flatMap!

// flatMap = map + flatten:
// Array<a>.flatMap((a) → Array<b>) → Array<b>

[1, 2, 3].flatMap((x) => [x, x * 10]);
// → [1, 10, 2, 20, 3, 30]
// Mỗi element → array mới → FLATTEN thành 1 array!

// SO SÁNH map vs flatMap:
[1, 2, 3].map((x) => [x, x * 10]);
// → [[1, 10], [2, 20], [3, 30]]   ← NESTED arrays!

[1, 2, 3].flatMap((x) => [x, x * 10]);
// → [1, 10, 2, 20, 3, 30]          ← FLAT!

// CHAIN flatMap:
["hello world", "foo bar"]
  .flatMap((str) => str.split(" ")) // → ['hello', 'world', 'foo', 'bar']
  .flatMap((word) => word.split("")); // → ['h','e','l','l','o',...];
```

```
SO SÁNH MONAD methods:

  ┌──────────────────┬────────────────────────────────────────┐
  │ Container        │ Monad method (bind)                    │
  ├──────────────────┼────────────────────────────────────────┤
  │ Promise          │ .then()                                │
  │ Array            │ .flatMap()                             │
  │ Option           │ .flatMap() hoặc .bind()                │
  │ Result           │ .flatMap() hoặc .andThen()             │
  │ Iterator/Stream  │ .flatMap() (generators)                │
  └──────────────────┴────────────────────────────────────────┘

  TẤT CẢ cùng 1 contract:
  M<a>.bind((a) → M<b>) → M<b>
```

### 12.6 Functor — Khái Niệm

```
FUNCTOR = container có method MAP:

  ┌─────────────────────────────────────────────────────────────┐
  │  CONTRACT:                                                  │
  │                                                             │
  │  container.map(regularFunction) → container MỚI cùng type  │
  │                                                             │
  │  F<a>.map((a) → b) → F<b>                                  │
  │                                                             │
  │  Trong đó:                                                  │
  │  → F = loại container (Array, Option, Result,...)          │
  │  → map nhận REGULAR function: (a) → b                      │
  │     (KHÔNG phải Kleisli arrow! Trả value, KHÔNG container) │
  │  → Trả về F<b> (CÙNG loại container, giá trị MỚI)         │
  └─────────────────────────────────────────────────────────────┘

  KHÁC BIỆT VỚI MONAD:

  Functor: F<a>.map((a) → b)    → F<b>     ← function trả VALUE
  Monad:   M<a>.bind((a) → M<b>) → M<b>     ← function trả CONTAINER

  → Functor = "áp dụng" function THƯỜNG lên container
  → Monad   = "chain" functions trả container
```

### 12.7 Functor Trong Thực Tế

```javascript
// ARRAY LÀ FUNCTOR — map!
["foo.txt", "bar.txt"]
  .map((file) => fs.readFileSync(file)) // → [Buffer, Buffer]
  .map((buffer) => buffer.toString("utf-8")); // → [string, string]

// .map() nhận REGULAR function: (a) → b
// Trả Array MỚI cùng type

// OPTION LÀ FUNCTOR:
findUser(42)
  .map((user) => user.name) // Option<string>
  .map((name) => name.toUpperCase()); // Option<string>
// Nếu None → map KHÔNG chạy, trả None!

// RESULT LÀ FUNCTOR:
parseJSON('{"x":1}')
  .map((obj) => obj.x) // Result<number>
  .map((x) => x * 2); // Result<number>
// Nếu Err → map KHÔNG chạy, trả Err!

// PROMISE LÀ FUNCTOR (khi then nhận regular function):
fetch("/api").then((res) => res.status); // Promise<number>
// (a) → b, KHÔNG phải (a) → Promise<b>
// → Promise TỰ ĐỘNG wrap giá trị thường!
```

```
MỌI MONAD đều là FUNCTOR:

  → Monad MẠNH hơn Functor
  → Có thể implement map BẰNG bind:
     container.map(f) = container.bind(x => wrap(f(x)))

  FUNCTOR chỉ map value → value
  MONAD có thể chain container → container

  ┌──────────────────────────────────────────────────────┐
  │                                                      │
  │          ┌─────────┐                                 │
  │          │ Functor │  ← map: (a) → b                │
  │          │         │                                 │
  │          │ ┌─────┐ │                                 │
  │          │ │Monad│ │  ← bind: (a) → M<b>            │
  │          │ └─────┘ │                                 │
  │          └─────────┘                                 │
  │                                                      │
  │  Monad ⊂ Functor (mọi Monad đều là Functor)       │
  └──────────────────────────────────────────────────────┘
```

### 12.8 Monoid — Khái Niệm

```
MONOID = type có 2 thứ:

  1. PHÉP CỘNG (binary operation): a ⊕ b → c
     → Kết hợp 2 giá trị CÙNG TYPE → giá trị MỚI cùng type
     → Phải ASSOCIATIVE: (a ⊕ b) ⊕ c = a ⊕ (b ⊕ c)

  2. NEUTRAL ELEMENT (identity): e
     → e ⊕ a = a   (thêm e không ảnh hưởng kết quả)
     → a ⊕ e = a
```

```javascript
// VÍ DỤ MONOID TRONG JS:

// String monoid: operation = +, neutral = ''
"" + "hello" === "hello"; // ✅ neutral + a = a
"hello" + "" === "hello"; // ✅ a + neutral = a
"a" + "b" + "c" === "a" + ("b" + "c"); // ✅ associative

// Number monoid (addition): operation = +, neutral = 0
0 + 42 === 42; // ✅ neutral + a = a
1 + 2 + 3 === 1 + (2 + 3); // ✅ associative

// Number monoid (multiplication): operation = *, neutral = 1
1 * 42 === 42; // ✅ neutral * a = a
2 * 3 * 4 === 2 * (3 * 4); // ✅ associative

// Array monoid: operation = concat, neutral = []
[]
  .concat([1, 2]) // [1, 2]  ✅ neutral
  [1].concat([2])
  .concat([3]); // = [1].concat([2, 3])  ✅ associative

// Boolean monoid (AND): operation = &&, neutral = true
// Boolean monoid (OR):  operation = ||, neutral = false
```

```
TẠI SAO MONOID QUAN TRỌNG?

  ┌─────────────────────────────────────────────────────────┐
  │  1. REDUCE/FOLD = áp dụng monoid lên collection!       │
  │                                                         │
  │     [1, 2, 3, 4].reduce((a, b) => a + b, 0)           │
  │     → 0 + 1 + 2 + 3 + 4 = 10                          │
  │       ↑                     ↑                          │
  │     neutral              operation                     │
  │                                                         │
  │  2. ASSOCIATIVE → có thể PARALLELIZE!                  │
  │     (1+2) + (3+4) = 1 + (2+3) + 4                     │
  │     → Chia nhỏ → tính song song → gộp lại!            │
  │                                                         │
  │  3. NEUTRAL element → base case cho recursion/fold     │
  │     → Không cần xử lý special case cho empty input     │
  └─────────────────────────────────────────────────────────┘
```

### 12.9 Tại Sao Interfaces Quan Trọng Hơn Types

```
TỪ CONCRETE TYPES → INTERFACES:

  ❌ Code phụ thuộc CONCRETE type:
  function processUsers(users: User[]) {
    return users.map(u => u.name);  // CHỈ hoạt động với Array!
  }

  ✅ Code phụ thuộc INTERFACE (Functor):
  function processData(container) {
    return container.map(u => u.name);  // Hoạt động với BẤT KỲ Functor!
  }
  // → Array, Option, Result, Promise, Stream,... đều OK!

  LỢI ÍCH:
  ┌─────────────────────────────────────────────────────────┐
  │  → Functions UNIVERSAL hơn                             │
  │  → ÍT functions hơn (1 function cho nhiều types)       │
  │  → Complex things = COMPOSITIONS of simple things     │
  │  → Dễ test, dễ maintain, dễ extend                    │
  │  → ĐÂY LÀ TRÁI TIM CỦA FP!                          │
  │     (không phải immutability như nhiều người nghĩ!)     │
  └─────────────────────────────────────────────────────────┘
```

### 12.10 FP Style Guidelines

```
CÁCH VIẾT CODE THEO FP STYLE:

  1. Mô tả MỌI THỨ bằng functions
  2. Kết quả function CHỈ phụ thuộc arguments (pure functions)
  3. Dùng simple types + container types
  4. Monad interface → chain containers
  5. Functor interface → transform data trong containers
  6. Ưu tiên INTERFACES, không concrete types

  KẾT QUẢ:
  → Code đơn giản, dễ test
  → Dễ mở rộng (thêm type mới → cùng interface)
  → Compositions mạnh mẽ
  → Ít bugs (type-safe, không quên handle errors)
```

## 13. CS Frontend: Async Iterators, Generators & Reactive Programming

> 📺 Nguồn: CS Frontend — Asynchronous Iterators & Generators. Reactive Data Structures

### 13.1 Nhắc Lại — Iterators & Iterable

```
ITERATOR = Finite State Machine cho việc duyệt data:

  ┌────────────────────────────────────────────────────────┐
  │  Iterator = object có method next()                      │
  │  next() → { done: boolean, value: any }                 │
  │    → done: false = còn data                             │
  │    → done: true  = HẾT data                             │
  │                                                          │
  │  Iterable = object có Symbol.iterator                    │
  │  Symbol.iterator() → iterator MỚI                       │
  │  → for-of, spread (...), destructuring dùng nó          │
  │                                                          │
  │  IterableIterator = iterator CŨNG có Symbol.iterator    │
  │  Symbol.iterator() → return THIS (chính nó!)            │
  │  → Truyền trực tiếp vào for-of, spread,...              │
  └────────────────────────────────────────────────────────┘
```

### 13.2 Đặc Điểm & Lazy Evaluation

```
LAZY EVALUATION — sức mạnh của iterators:

  → Chỉ thực thi KHI GỌI next() (lazy, không eager)
  → Xử lý VỮA ĐỦ (đúng số lượng cần)
  → Mô tả được iterators VÔ HẠN (infinite)
  → Xây dựng COMPOSITIONS (monadic, functor interfaces)

  EAGER vs LAZY:
  ┌───────────────────────────────────────────────────────┐
  │  EAGER (Array methods):                                │
  │  [1,2,3,4,5].filter(x => x > 2).map(x => x * 2)      │
  │  → Tạo array TRUNG GIAN [3,4,5] rồi [6,8,10]         │
  │  → Xử lý TOÀN BỘ dữ liệu ngay lập tức!              │
  │                                                         │
  │  LAZY (Iterator):                                      │
  │  take(3, filter(x => x > 2, range(1, Infinity)))      │
  │  → Chỉ xử lý đến khi có đủ 3 kết quả!              │
  │  → KHÔNG tạo array trung gian!                        │
  │  → Hoạt động với INFINITE data!                       │
  └───────────────────────────────────────────────────────┘

  ⚠️ LưU Ý: Iterators có PERFORMANCE COST trong JS
  → Dùng chủ yếu cho API design + complex compositions
  → Kết hợp eager (.map, .filter) với lazy (iterators) để
    đạt hiệu quả tốt nhất!
```

### 13.3 Nhắc Lại — Generators

```
GENERATOR = coroutine đặc biệt:

  → Khai báo: function*
  → Tạm dừng: yield (trả value, save state!)
  → Ủy quyền: yield* (delegate cho iterator khác)
  → Từ bên ngoài: TRÔNG GIỐNG iterator!
  → Mở rộng: có thêm return() và throw() methods
```

```javascript
// GENERATOR = cách viết iterator ĐƠN GIẢN NHẤT:
function* range(start, end) {
  for (let i = start; i < end; i++) {
    yield i; // TẠM DỪNG + trả value + SAVE STATE!
  }
}

for (const n of range(0, 5)) {
  console.log(n); // 0, 1, 2, 3, 4
}

// TRUYỀN VALUE VÀO generator:
function* accumulator() {
  let total = 0;
  while (true) {
    const value = yield total; // nhận value từ next(value)
    total += value;
  }
}

const acc = accumulator();
acc.next(); // { value: 0, done: false }  (khởi động)
acc.next(10); // { value: 10, done: false }
acc.next(20); // { value: 30, done: false }
acc.next(5); // { value: 35, done: false }

// RETURN và THROW:
// gen.return(value) → kết thúc generator, { done: true, value }
// gen.throw(error)  → throw error BÊN TRONG generator
// for-of gọi return() tự động khi break/return/throw!
```

### 13.4 Vấn Đề — Generators Là SYNC!

```
GENERATORS hoạt động SYNCHRONOUSLY.
Nhưng nếu cần iterate qua data ASYNC (server, events)?

  THử 1: Cho value là Promise:
  ┌──────────────────────────────────────────────────────┐
  │  next() → { done: ???, value: Promise<data> }          │
  │                                                        │
  │  ❌ VẤN ĐỀ: không biết done là gì!                    │
  │  → Promise chưa resolve → không biết còn data không! │
  │  → for-of KHÔNG hiểu Promise!                         │
  └──────────────────────────────────────────────────────┘

  THử 2: next() trả Promise<{done, value}>:
  ┌──────────────────────────────────────────────────────┐
  │  next() → Promise<{ done: boolean, value: data }>     │
  │                                                        │
  │  ✅ done và value đến CÙNG LÚC!                        │
  │  ❌ Vi phạm contract của Iterator!                     │
  │  ❌ for-of, spread VẪN không hoạt động!               │
  └──────────────────────────────────────────────────────┘

  GIẢI PHÁP: TẠO TYPE MỚI — AsyncIterator!
```

### 13.5 AsyncIterator & async function\*

```
ASYNC ITERATOR = iterator cho DATA KHÔNG ĐỒNG BỘ:

  ┌──────────────────────────────────────────────────────────┐
  │  Iterator (sync):                                        │
  │  next() → { done, value }                               │
  │  Symbol.iterator → iterator                             │
  │  for-of                                                  │
  │                                                          │
  │  AsyncIterator:                                          │
  │  next() → Promise<{ done, value }>                      │
  │  Symbol.asyncIterator → async iterator                  │
  │  for await of                                            │
  │                                                          │
  │  async function* = async generator (coroutine)           │
  │  → Kết hợp function* + async/await!                     │
  └──────────────────────────────────────────────────────────┘
```

### 14.5 Semaphore

```
SEMAPHORE = container GIỚI HẠN truy cập tài nguyên:

  ┌──────────────────────────────────────────────────────────┐
  │  Có COUNTER nội bộ (max N consumers)                     │
  │  acquire() → counter-- (nếu > 0, cho truy cập)         │
  │           → nếu counter = 0 → CHỜ!                     │
  │  release() → counter++ (giải phóng slot)                │
  │                                                          │
  │  ⚠️ QUÊN release() = DEADLOCK!                           │
  └──────────────────────────────────────────────────────────┘

  VÍ DỤ: Rate-limiting API requests (max 3 đồng thời):

  Semaphore(3):  [slot1] [slot2] [slot3]

  Request A → acquire ✅ (counter: 2)
  Request B → acquire ✅ (counter: 1)
  Request C → acquire ✅ (counter: 0)
  Request D → acquire ⏳ CHỜ! (counter = 0)
  Request A hoàn thành → release (counter: 1)
  Request D → acquire ✅ (counter: 0)
```

```javascript
// SEMAPHORE implementation:
class Semaphore {
  constructor(max) {
    this._max = max;
    this._count = 0;
    this._queue = [];
  }

  acquire() {
    return new Promise((resolve) => {
      if (this._count < this._max) {
        this._count++;
        resolve();
      } else {
        this._queue.push(resolve); // CHỜ trong queue!
      }
    });
  }

  release() {
    if (this._queue.length > 0) {
      const next = this._queue.shift();
      next(); // cho consumer tiếp theo vào!
    } else {
      this._count--;
    }
  }
}

// Dùng — rate-limit API:
const limiter = new Semaphore(3); // max 3 requests

async function fetchWithLimit(url) {
  await limiter.acquire(); // chờ slot trống
  try {
    return await fetch(url);
  } finally {
    limiter.release(); // LUÔN release!
  }
}

// Gửi 100 requests, chỉ 3 chạy đồng thời:
await Promise.all(urls.map(fetchWithLimit));
```

### 14.6 Mutex & ReadWriteLock

```
MUTEX = SEMAPHORE với max = 1:

  → CHỈ 1 consumer tại 1 thời điểm
  → CHỈ entity đã acquire MỚI ĐƯỢC release
  → Ngăn hoàn toàn data races

  VÍ DỤ: Google Docs — nhiều người XEM,
  nhưng chỉ 1 người EDIT cell tại 1 thời điểm!

  Users:  [Alice-view✅] [Bob-view✅] [Charlie-edit🔒]
  Cell A1: LOCKED bởi Charlie → Alice/Bob chờ nếu muốn edit
```

```
READWRITELOCK (RWLock):

  ┌──────────────────────────────────────────────────────────┐
  │  Cho phép NHIỀU readers HOẶC DUY NHẤT 1 writer:         │
  │                                                          │
  │  Internal counter bắt đầu = 0:                           │
  │                                                          │
  │  READ:  counter >= 0 → cho phép (counter++)              │
  │         Khi xong → counter--                             │
  │                                                          │
  │  WRITE: CHỈ khi counter = 0 (không ai đọc/ghi)          │
  │         Lock → counter = -1                              │
  │         Khi xong → counter = 0                           │
  │                                                          │
  │  KẾT QUẢ: ∞ readers HOẶC 1 writer → AN TOÀN!           │
  └──────────────────────────────────────────────────────────┘

  Timeline:
  ──[R1 read]──[R2 read]──[R3 read]── → ĐỒNG THỜI OK!
  ──────────────────────────[W1 write]── → CHỈ MÌNH W1!
  ──[R4 read]──[R5 read]────────────── → readers LẠI vào!
```

```javascript
// MUTEX implementation (Semaphore max=1):
class Mutex extends Semaphore {
  constructor() {
    super(1);
  }

  async runExclusive(fn) {
    await this.acquire();
    try {
      return await fn();
    } finally {
      this.release();
    }
  }
}

// Dùng:
const mutex = new Mutex();

async function updateSharedState(newValue) {
  return mutex.runExclusive(async () => {
    const current = await readState();
    await writeState(current + newValue); // AN TOÀN!
  });
}
```

```
  → Khi conditions đủ → function THỰC THI!

  VÍ DỤ: App initialization
```

```javascript
// ASYNC SEMAPHORE / BARRIER:
class AsyncBarrier {
  constructor(count) {
    this._remaining = count;
    this._promise = new Promise((resolve) => {
      this._resolve = resolve;
    });
  }

  signal() {
    this._remaining--;
    if (this._remaining <= 0) {
      this._resolve(); // TẤT CẢ conditions đã thỏa!
    }
  }

  async wait() {
    await this._promise; // CHỜ cho đến khi đủ signals
  }
}

// Dùng cho app init:
const appReady = new AsyncBarrier(3);

loadAuth().then(() => appReady.signal()); // 1/3
loadTranslations().then(() => appReady.signal()); // 2/3
loadABTests().then(() => appReady.signal()); // 3/3

await appReady.wait();
renderApp(); // CHỈ chạy khi CẢ 3 xong!
```

```
  │  ├──────────────┴─────────────────┴───────────┤   │
  │  │  Thread 1 (stack riêng)  │  Thread 2 (stack riêng) │   │
  │  │  CHIA SẺ Heap!          │  CHIA SẺ Heap!         │   │
  │  └────────────────────────┴────────────────────────┘   │
  └──────────────────────────────────────────────────────────┘

  → Threads nhẹ hơn processes (chia sẺ heap)
  → NHƯNG: chia sẺ heap = NGUY HIỂM (data races!)

MULTITHREADED ≠ CONCURRENCY (luôn là)!

  → Nếu threads KHÔNG chia sẺ data (hoặc không mutate)
  → "Shared-nothing" pattern = không concurrency issues!
  → KHÔNG cần locks, không data races!
```

### 15.2 Amdahl's Law & Nguy Hiểm

```
AMDAHL'S LAW:

  → Parallelism chỉ nhanh hơn NẾU threads làm việc ĐỘC LẬP
  → Tốc độ bị GIỚI HẠN bởi thread CHẬM NHẤT
  → Chi phí tạo thread > thời gian thực thi → VÔ ÍCH!

  VÍ DỤ:
  ┌───────────────────────────────────────────────────────┐
  │  Sequential: ───[Task A: 100ms]───[Task B: 10ms]───  │
  │  Total: 110ms                                        │
  │                                                       │
  │  Parallel:   Thread 1: ─[Task A: 100ms]──────────  │
  │              Thread 2: ─[Task B: 10ms]──              │
  │  Total: 100ms + overhead = ~102ms                    │
  │  → Chỉ nhanh hơn 7%! (bottleneck = Task A)            │
  └───────────────────────────────────────────────────────┘

NGUY HIỂM KHI CHIA SẺ DATA:

  Thread 1 ghi: [A1][A2][A3][A4]
  Thread 2 ghi: [B1][B2][B3][B4]
                     ↓
  Kết quả:     [A1][B2][A3][B4]  ← DATA CORRUPTION!
  → Undefined Behavior (UB)!

GIẢI PHÁP:
  ┌───────────────────────────────────────────────────────┐
  │  1. Shared-nothing: KHÔNG chia sẺ data                │
  │  2. Immutability: không mutate shared data              │
  │  3. Locks: Mutex, RWLock (đã học §14)                  │
  │  4. Data Ownership: chuyển quyền, gốc mất access    │
  │  5. Atomics: operations nguyên tử, không bị interrupt   │
  │  6. Memory Model: volatile, synchronized (Java)       │
  └───────────────────────────────────────────────────────┘
```

### 15.4 Truyền Data Giữa Threads

```
3 CÁCH truyền data giữa threads trong JS:

  ┌──────────────────┬────────────┬────────────┬────────────┐
  │                  │ Copy         │ Transfer     │ Shared       │
  ├──────────────────┼────────────┼────────────┼────────────┤
  │ Cơ chế           │ structuredCl │ Transfer     │ SharedArray  │
  │                  │ one (deep)   │ ownership    │ Buffer       │
  │ Gốc giữ data?    │ CÓ (copy)    │ MẤT access   │ CẢ 2 truy cập│
  │ Tốc độ           │ Chậm (copy) │ NHANH (move) │ Nhanh       │
  │ An toàn          │ ✅ (no share) │ ✅ (no share) │ ⚠️ Cần Atomics│
  │ Data types       │ Objects,     │ ArrayBuffer  │ SharedArray │
  │                  │ arrays,...   │ MessagePort  │ Buffer      │
  │                  │ (❌ functions)│ OffscreenCnv │             │
  └──────────────────┴────────────┴────────────┴────────────┘
```

```javascript
// CÁCH 1: COPY (structuredClone) — postMessage tự deep clone:
worker.postMessage({ users: bigArray });
// → bigArray được DEEP COPY sang worker
// → An toàn nhưng CHẬM với data lớn!

// CÁCH 2: TRANSFER OWNERSHIP — chuyển quyền!
const buffer = new ArrayBuffer(1024 * 1024); // 1MB
console.log(buffer.byteLength); // 1048576

worker.postMessage(buffer, [buffer]); // transfer!
console.log(buffer.byteLength); // 0! ← MẤT ACCESS!
// → Worker có TOÀN QUYỀN, main thread MẤT!
// → KHÔNG cạnh tranh → AN TOÀN + NHANH!

// CÁCH 3: SHARED MEMORY (SharedArrayBuffer + Atomics):
const shared = new SharedArrayBuffer(1024);
const view = new Int32Array(shared);

worker.postMessage(shared);
// → CẢ HAI threads truy cập CÙNG memory!
// → CẦN Atomics để đọc/ghi AN TOÀN!

// Atomics API:
Atomics.store(view, 0, 42); // ghi ATOMIC
const val = Atomics.load(view, 0); // đọc ATOMIC
Atomics.add(view, 0, 10); // cộng ATOMIC
Atomics.compareExchange(view, 0, 42, 99); // CAS

// Synchronization:
Atomics.wait(view, 0, 0); // SLEEP thread cho đến khi value thay đổi
Atomics.notify(view, 0, 1); // ĐÁNH THỨC 1 thread đang wait
```

```
⚠️ SharedArrayBuffer cần CORS headers:

  Cross-Origin-Opener-Policy: same-origin
  Cross-Origin-Embedder-Policy: require-corp

  → Bắt buộc! Không có = SharedArrayBuffer bị DISABLE!
  → Bảo mật chống Spectre/Meltdown side-channel attacks
```
